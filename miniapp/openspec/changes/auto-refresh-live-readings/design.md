## Context

- 首页 `onShow` 调 `loadHome()`，每台设备读一次 `telemetry/latest`；另有一个 60 秒的定时器只刷新罐形（`shapeTimer`），不刷新读数。
- 详情页 `onShow` 调 `refreshActiveTab()`，`snapshot` tab 读一次 latest；同样有 60 秒的罐形定时器。
- 两个页面都已有"刷新失败时保留旧读数并提示"的逻辑（`staleText` / `fetchedAt`）和防止旧请求覆盖新结果的序号（`loadSeq`）。

## Goals / Non-Goals

**Goals：** 停在页面上就能在几秒内看到设备的新读数，不需要下拉。

**Non-Goals：**
- 不做云端 WebSocket 推送。
- 不改出入库、报警、命令等其他列表的刷新方式。

## Decisions

### 1. 用定时轮询，而不是云端推送

可选方案：
- **A. 小程序每 5 秒轮询 `telemetry/latest`（选这个）**：只改小程序，接口现成，几行代码。
- **B. 云端推送**：云端 `internal/ingest` 已经订阅了每台设备的 ThingsBoard 遥测，但收到快照后直接丢弃；要做推送，得在云端把快照转发到 Redis 和一个新的 WebSocket 端点，小程序再接入。延迟能做到 1–2 秒，但要改云端、改契约。

现在用户和设备都不多，5 秒的轮询延迟已经能解决"半分钟"的问题，所以先用 A。以后用户量变大或要求秒级，再做 B。

### 2. 轮询间隔 5 秒

和设备端变化触发的最短间隔一致，再短也拿不到更新的数据。

### 3. 只在真正可见时轮询

用页面的 `onShow` / `onHide` / `onUnload` 控制：小程序切到后台时也会触发 `onHide`，所以不需要额外处理。详情页只在当前 tab 是 `snapshot` 时运行定时器，切 tab 时启停。

### 4. 复用现有的加载与失败处理

- 首页：把 `loadDevice` 里读 latest 的部分拆成 `loadTelemetry`，定时器只调它（不重读罐形）；每台设备有在途计数，未返回就跳过。
- 详情页：`loadSnapshot(silent)`，静默时不设 `loading`、不重读罐形、失败不弹提示（403 除外，它会让页面回到未加载状态，之后不再轮询）。
- 失败时保留旧读数，现有的过期提示照常出现。

## Risks / Trade-offs

- **[一个用户关注多台设备时，每 5 秒发多个请求]** → 首页本来就是逐台读，请求量和设备数成正比。目前每个账号的设备数很少，可以接受。
- **[请求慢于 5 秒]** → 用"上一次没返回就跳过"避免请求堆积。
