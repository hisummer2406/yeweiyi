# 容量与压测报告

GitHub issue #5 的交付物。**这份报告只覆盖它的一部分** —— 未做的部分在末节明确列出，请连同一起读。

工具：`cmd/loadtest`，可重复执行。报告里的每个数字都能用文中给出的命令复现。

---

## 先说清楚这次测到了哪、没测到哪

| 场景 | 状态 |
|---|---|
| 1,000 台持续遥测基线 | ❌ **未达成**，本机硬件不足，见"硬件天花板" |
| 10,000 台容量测试 | ❌ 未做，需要真实服务器与集群拓扑 |
| 每条快照按真实数据点数构造 | ✅ 26 点/快照（2 罐），与协议一致 |
| 100% 重连风暴 | ✅ 200 台规模已测 |
| 报警突发、RPC 并发、WebSocket 订阅 | 部分：WebSocket 订阅在测（延迟采样即走 WS），报警与 RPC 并发未压测 |
| 组件故障/恢复 | ❌ 未做 |
| 7 天 TTL 与汇总任务同时运行 | ❌ 未做（TTL/汇总本身尚未实现） |

**本次实测规模是 200 台。** 拿它当 1,000 台的结论用是错的；它能支撑的结论只有下面写明的那些。

## 测试环境

```
主机     macOS darwin/amd64，4 核，8 GB 内存（Docker Desktop 分得 3.8 GB）
容器     ThingsBoard CE 4.2.1.1（tb-postgres），JAVA_OPTS -Xms1G -Xmx2G
         PostgreSQL 16、Redis 7
设备     每台 2 罐 = 26 数据点/快照，30 秒周期（生产节奏）
```

⚠️ **这是一台开发笔记本，不是服务器。** 下面的数字用于建立下限与验证工具，不能直接当作生产容量。

## 结果：200 台稳态

```bash
loadtest -devices 200 -duration 90s -ramp 20s -interval 30s -latency-sample 10
```

| 指标 | 实测 |
|---|---|
| 设备开通速率 | 58 台/秒 |
| 建连 | 200/200 成功 |
| 稳态吞吐 | **174 数据点/秒**（目标 173，即 100%） |
| 快照失败 | 0 / 601 |
| 端到端延迟 | **p50 56ms、p95 111ms、p99 121ms、max 121ms** |
| ThingsBoard CPU | 约 23% |
| ThingsBoard 内存 | 1.97 GiB / 2 GiB 堆上限 |

端到端延迟的定义：设备发布时刻 → 后台经 ThingsBoard WebSocket 看到该值。两个时刻取自同一进程
的同一个时钟，无时钟偏差可言。

## 结果：100% 重连风暴

```bash
loadtest -devices 200 -duration 3m -ramp 20s -interval 30s -reconnect-pct 100 -reconnect-at 60s
```

| 指标 | 实测 |
|---|---|
| 断开并同时重连 | 200 台（100%），**无退避、无铺开** |
| 全部恢复用时 | **390 ms** |
| 期间丢失快照 | 1 条（断开瞬间在途的那条） |
| 恢复后吞吐 | 立即回到 173 数据点/秒 |
| 端到端延迟 | p50 69ms、p95 124ms、p99 132ms |

风暴是**最坏情况**：全部设备在同一瞬间重连，不加任何退避。真实设备侧有 2s 起、上限 60s 的
指数退避加抖动（`docs/protocol-v1.md` §9），所以现场的风暴只会比这个更缓和。

这是 issue #1 点名担心的场景，在 200 台规模上**没有观察到问题**。

## 硬件天花板：500 台失败了，以及为什么

500 台的运行 **10 分钟内只开通了约 109 台**便被中止。同一时刻 ThingsBoard 内存
**1.94 GiB / 2 GiB 堆上限**、CPU 147%。

值得注意的是：中止后立刻测删除速度是 **59 台/秒** —— 也就是说 API **并未永久劣化**，
慢是负载期间的堆压力造成的，而非某种泄漏或死锁。

200 台时内存已经是 1.97 GiB，同样贴着 2 GB 堆上限。所以在这台机器上：

- **堆是绑定约束，不是 CPU**（200 台时 CPU 才 23%）；
- 提高堆需要更多物理内存，而本机 Docker 只有 3.8 GB 可分；
- 因此 **1,000 台无法在此机器上验证**，这是环境限制，不是被测系统的结论。

---

## 能支撑的结论

**小型私有化档（≤100 台）已被验证，且有 2 倍余量。** `deploy/profiles/small.yml` 给 ThingsBoard
2–3 GB 堆；实测 200 台在 2 GB 堆下稳态零错误、p95 延迟 111ms。100 台的目标规模有充分余量。

**重连风暴在该规模下不是问题。** 100% 同时重连 390ms 全部恢复。

**扩容的第一杠杆是堆内存，不是 CPU。** 200 台时 CPU 仅 23% 而堆已满。`deploy/profiles/cloud.yml`
按这个方向给 4–8 GB 堆是对的。

## 不能支撑的结论

- **1,000 台的推荐规格**：没测到，`cloud.yml` 里的数字仍是算术推导。
- **10,000 台的扩容拓扑**：完全未验证。单节点大概率不够，需要 ThingsBoard 集群
  （Kafka 队列 + 多传输节点），那是另一套部署形态。
- **磁盘 IO 与数据库增长**：本次未测量。200 台跑 3 分钟的数据量太小，看不出增长趋势。
- **长时间稳定性**：最长一次运行 3 分钟。内存泄漏、GC 退化、磁盘写满都需要小时级测试。

## 怎么在真实硬件上跑

```bash
# 基线
loadtest -devices 1000 -duration 30m -ramp 5m -interval 30s -latency-sample 50

# 重连风暴（先稳态 10 分钟，再 100% 同时重连）
loadtest -devices 1000 -duration 30m -reconnect-pct 100 -reconnect-at 10m

# 逐档找天花板
for n in 1000 2000 5000 10000; do loadtest -devices $n -duration 10m; done
```

跑之前：

- 把 ThingsBoard 堆按 `deploy/profiles/cloud.yml` 调大，并确认物理内存足够；
- 压测客户端**放在另一台机器上**。本次是同机运行，客户端自身的 1,000 条 MQTT 连接会与被测
  服务抢 CPU 和内存，规模一大就分不清瓶颈在哪一边；
- 同时采集 ThingsBoard、PostgreSQL 的 CPU/内存/磁盘 IO 与数据库体积增长；
- 工具会自建设备并在结束时删除，但**进程被强杀时清理不会执行**（本次超时中止就留下了 109 台）。
  按 `loadtest-` 前缀清理即可。

## 副产物：测试套件的并行争用

压测把 ThingsBoard 灌进了数据之后，`go test ./...` 并行跑开始偶发失败
（`TestFullLoop_CommandReachesTerminalStateViaIngest`，3 次里 2 次，均卡在 25 秒超时）。

原因是争用而非缺陷：`internal/api`、`internal/tbclient`、`internal/ingest` 三个包同时压同一个
ThingsBoard，而开发机上压测客户端与服务端共用 CPU。单包跑、串行跑均全绿，ThingsBoard 自身健康
（队列 `totalFailed [0]`）。**用 `-p 1`。**

这也是"压测客户端必须放在另一台机器上"那条建议的现场例证——同机运行时，分不清慢的是哪一边。

## 工具本身的一处教训

第一版在重连风暴触发的瞬间 panic：`d.sim` 被风暴协程置 nil 的同时，发布协程正在读它 —— 一个
没有加锁的字段被两个协程同时读写。已改为互斥量保护的访问器，并用 `go build -race` 复跑确认
无数据竞争。

**压测工具本身也要在竞态检测器下跑过**：它天生是高并发的，而它一崩就会留下几百台测试设备，
且让人误以为是被测系统的问题。
