# 小程序设计稿对云端接口的缺口清单

**状态：待评审，非规范文档，供产品/后端决策参考。** 2026-09-10 由 `yeweiyi-miniapp` 整理。

## 背景

`yeweiyi-miniapp/docs/智能液位仪-小程序.psd` 有 28 个画板，比该仓库 `CLAUDE.md` 记录的 5 页/
现有接口范围大得多。视觉规范（配色/字号/组件样式）已经整理进小程序前端，不需要后端配合；但其中
一部分画板背后的功能，云端要么没有对应接口，要么方法已经在 `internal/protocol/rpc.go` 的
`Methods` 表里挂了名字但参数结构（`Envelope.Args`）从未定义。这份文档只整理**功能性缺口**，
逐条对照当前代码确认过，不是照抄设计稿的猜测。

小程序这边的处理方式：这些功能目前只做成 `pages/more/more` 之下的几个静态预览页，不发起任何真实
请求，界面上会说明"设计稿有、云端暂无接口"，避免在契约没定之前假装功能存在。

---

## 一、已有方法名、只是参数结构未定义（补齐 schema 即可，不用新增方法）

### 1. `config.setTank`（画板：储罐设置10 上半部分）

`Methods` 表里已经有这个方法（PermAdmin），但 `Envelope.Args` 是 `json.RawMessage`，没有任何
字段约定。设计稿给出的表单字段，可以作为参数 schema 的第一版草案：

| 字段 | 控件 | 单位 |
|---|---|---|
| 罐号 | picker | — |
| 传感器ID | picker | — |
| 储罐类型 | picker（卧罐/立罐/长方体，对应画板 罐表设置15-19） | — |
| 物料颜色 | picker | — |
| 介质密度 | 数字输入 | kg/m³ |
| 储罐高度 | 数字输入 | 毫米 |
| 储罐容量 | 数字输入 | 升 |

### 2. `config.setAlarmThresholds`（画板：储罐设置10 下半部分）

同样已有方法名、无参数结构。设计稿字段：

| 字段 | 单位 |
|---|---|
| 高高液位报警 / 高液位报警 / 低低液位报警 / 低液位报警 | 毫米 |
| 高水位报警 / 低水位报警 | 毫米 |
| 高温报警 / 低温报警 | ℃ |

**需要决定一件事**：设计稿把这两组字段放在同一张"储罐设置"表单里一次性提交，但接口侧是
`config.setTank` 和 `config.setAlarmThresholds` 两个不同方法。前端拆成两次下发，还是后端提供
一个组合端点，需要定下来。

## 二、目前完全没有对应方法/接口（需要新增，或明确不做）

### 3. 传感器读数校准（画板：参数修正07/08/09）

不是"修正已有出入库记录"，是液位/水位/温度的**校准偏移量**，表单是"罐号 + 液位修正/水位修正/
温度修正"三个数值，提交时二选一目标：

- "保存到手机" —— 纯本地存储，前端可以直接做，不需要接口；
- "保存到控制器" —— 需要下发给设备，`Methods` 里没有任何 calibrate 类方法，需要新增（例如
  `config.setCalibration`）或者决定并入 `config.setTank`。

### 4. 罐表（液位-容积换算表）生成与下发（画板：罐表设置15-19）

流程是：选罐体形状（卧罐/立罐/长方体）→ 输入物理尺寸（卧罐是 H/L/R）→ "生成罐表"（本地计算出
一张液位→容积的换算表）→ "保存到手机" / "保存到控制器"。

这是一项全新能力：协议里没有下发"一张表"（可能几十到几百行数据）给设备的方法，
`Envelope.Args` 能否装下这个体量也要评估。建议单独立项，不要顺带塞进 `config.setTank`。

### 5. 设备侧记录生命周期管理（画板：记录设置20、记录设置-弹窗21）

对**报警 / 入库 / 出库 / 交班 / 库存**五类记录，分别有"生成开关""删除开关""清空"三个操作，
"清空"有二次确认弹窗（文案："谨慎！是否清空记录，记录无法恢复"）。另外"库存记录"这一类还有
独立的生成周期设置（"库存生成时间 N 分"）。

需要产品先决定：

- 协议/API 目前完全没有"清空设备侧记录"这类方法——这类操作一旦误触就是数据永久丢失，权限至少
  要与现有 `config.*`（PermAdmin）持平，甚至需要比 `reason` 二次确认更强的校验；
- **"库存记录"是一个全新的记录类型**，不在 CLAUDE.md 记录的任何一条现有 API 里，需要先确认
  设备端是否已经在生成/上报这类数据，还是整个链路都要从头设计。

### 6. 报表导出（画板：报表设置22）

对报警/出库/入库/交班/库存五类记录分别有"导出"开关。目前 `/api/alarms`、`/api/oil-in-out`
之外没有任何导出成文件（Excel/CSV/PDF）的接口。

### 7. 出入库补录（画板：补录记录）

**这个和 CLAUDE.md 里"出入库记录修正无可行设计"是两件不同的事，不要合并讨论**：

- "记录修正"（CLAUDE.md 已有定论）：改写设备已经上报、已经落库的记录，要处理与设备侧数据的
  一致性冲突，`docs/protocol-v1-reconciliation.md` 里也没有给出方案。
- "补录"（这个画板）：手工**新增**一条历史上漏报的记录（罐号 + 时间 + 补录前高度 + 升数），
  本质是插入一条新数据，不涉及改写设备已上报的内容，技术复杂度应该低得多。如果产品需要，建议
  单独评估这条，不要因为"记录修正没法做"就连带否掉这个。

### 8. 交班记录（画板：首页-我的记录04 菜单项）

`docs/protocol-v1-reconciliation.md`「尚未有任何一方实现的：出入库与交班」一节已经记录：协议 V1
没有交班上行数据，`/api/shifts` 现在读的是旧栈才会写的表，单栈部署下永远返回空。设计稿仍然保留
了交班记录的入口——说明产品侧可能还是要这个功能，建议和后端一起把那份文档列的三个待决问题
（是否属于单栈启动范围 / 做成事件上报还是保留查询语义 / `CommitWork.info` 的结构化程度）一起定下来，
不要让这份新清单和那份旧清单各说各话。

### 9. 组织 / 多用户协作模型（画板：员工管理、邀请加入、邀请加入-输入、油站选择）

设计稿隐含一套完整的组织架构：

- **"油站"（站点）是比"设备"更高一级的分组实体**，有名称 + 地址，一个账号可以属于/切换多个油站；
- 一个油站下可以"邀请加入"其他账号（微信邀请或手机号邀请）共同管理设备；
- "员工管理"用于查看/管理已加入这个油站的账号。

目前 `yeweiyi-cloud` 的鉴权模型是单账号 + 三级角色（`platform_admin`/`customer_admin`/
`customer_user`），`GET /api/devices` 直接返回该账号绑定的设备列表，**没有"站点"这一层分组，
也没有"邀请其他账号共享设备"的机制**。这不是参数缺失，是数据模型缺一层，会牵动 users/devices
表结构，成本明显高于前面几条，建议单独开产品会决定要不要做，不适合在这份清单里顺带拍板。

补充：PSD 里"员工管理"这个画板本身是空的（图层树 0 个子节点），这块设计可能也没做完，仅供参考，
不代表产品侧已经想清楚了这个功能该长什么样。

---

## 三、明确不需要新接口的

- **设备添加**（画板：首页-添加 里的"添加设备"菜单项）：功能已经由现有
  `wx.scanCode()` + `POST /api/devices/bind` 覆盖，画板只是换了个入口样式，不需要改动接口。

## 建议的下一步

1. 逐条决定：哪些属于"单栈启动范围"，哪些明确砍掉、哪些延后——尤其是第九条（组织模型），
   这是数据模型级别的决定，成本和前面几条不是一个量级。
2. 第一、二节里如果确认要做，请后端基于本文档给的字段草案定稿参数 schema，前端再对齐
   `types/api.d.ts` 和 `utils/labels.ts`。
3. 第八条（交班）和已有的 `docs/protocol-v1-reconciliation.md` 合并决策，不要产生两份互相不
   知道对方存在的待办清单。
