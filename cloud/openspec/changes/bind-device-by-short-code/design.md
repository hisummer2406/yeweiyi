## Context

- 现状：`bindDeviceHandler` 先 `verifyPairingToken`（bcrypt 比对，无密钥时与假哈希比对以求时序一致），再 `EnsureDevice`，再 `BindUserDeviceIfAllowed`。后者在一条语句内锁用户行、设备行，校验“平台管理员，或设备归属 == 用户所属客户”，并幂等插入 `user_devices`。
- 设备名是业务库 `devices.device_name`（字符串，保留前导零）；客户管理员在管理后台登记设备并分配客户，所以“设备已分配给该客户”是已有的、由管理员控制的事实。
- 二维码只有短码；密钥不在二维码里。
- 小程序的使用者主要是 `customer_user`，带密钥路径今天就允许同客户任何角色绑定。

## Goals / Non-Goals

**Goals**
- 客户管理员扫短码即可绑定本客户已分配的设备。
- 不让短码绑定成为跨客户的设备存在性/归属预言机。
- 短码路径的可绑范围不大于带密钥路径（同客户成员 → 本客户设备）。
- 不破坏现有带密钥的绑定。

**Non-Goals**
- 申请、管理员批准的流程（同客户成员直接绑定，与带密钥路径一致）。
- 改二维码格式、改配对密钥铸造。
- 请求频率限制（见风险）。

## Decisions

1. **同一端点，`pairingToken` 可选**，而不是新端点。小程序已在调用它，带密钥路径零改动；缺省即走短码路径。备选“新增 `/devices/bind-by-code`”被否：两个端点要保持同样的错误一致性，更易漂移。
2. **解析发生在 SQL 里、限定在调用者客户内**，不在 Go 里先查再绑。候选名由 handler 生成：`[原文, 前缀1+原文, ...]`（原文需通过格式校验，见 3），查询在 `d` 子查询中取 `device_name = ANY(候选) AND customer_id = u.customer_id`，按“精确匹配优先、再按候选顺序”取一行并 `FOR SHARE`，然后沿用现有插入。这样“解析 + 授权 + 插入”仍是一条语句，转移竞态保证不变。
3. **原文格式校验**：只接受 `^[0-9A-Za-z]{1,32}$`；不满足直接按失败（统一 401），避免把任意字符串带进 `LIKE`/日志。不使用 `LIKE`，只用等值，避免通配符。
4. **角色**：SQL 中 `u.role IN ('customer_admin','customer_user') AND u.customer_id IS NOT NULL`。`platform_admin` 在短码路径被拒（没有所属客户，无法限定解析范围，且已有带密钥路径可用）。
5. **前缀来自配置**（默认 `ZCT`），而不是写死在 handler。各型号规则未确认，云端不得把前缀写成协议；配置为空列表时只做精确匹配。
6. **错误一致**：短码路径所有失败返回同一 401 `{"error":"invalid device name or pairing token"}`（沿用现有文案，避免客户端分叉）。短码路径没有 bcrypt，单次耗时与带密钥路径不同，但攻击者选择的是请求形状而非预言机；路径内部各失败原因走同一条 SQL，耗时一致。
7. **响应**：`{"deviceName": <解析后的完整名>, "bound": true}`。带密钥路径同样返回其入参名，行为不变。
8. **`EnsureDevice` 不用于短码路径**：短码只能绑定已存在且已分配给该客户的设备，不得凭一个短码创建设备行。

## Risks / Trade-offs

- **同客户内可枚举**：同客户成员可以枚举 6 位短码，但只能命中本客户已有设备，等价于他本来就有权访问；不构成跨租户风险。若以后要防“管理员误绑同客户别的油站的设备”，那是油站授权问题，不在此处。
- **爆破/限频**：端点没有限频；跨客户必然 401，价值很低，暂不加，列为后续。
- **前缀歧义**：若同客户存在 `000001` 与 `ZCT000001`，精确匹配优先，可能绑到非用户期望的那台。出厂编号规则确认后可收紧。
- **同客户任何成员都能绑本客户任何设备**：与带密钥路径一致，但带密钥路径要求拿到标签上的密钥，短码路径只要求同客户。若以后要按油站/员工授权，属于油站管理员与按用户授权的范围（cloud#44），不在此处。

## Open Questions

- 出厂编号是否一律为“前缀 + 6 位”？前缀集合还有哪些？
- 绑定动作是否要写审计日志（现有带密钥路径是否已写，实现时核对，保持一致）。
