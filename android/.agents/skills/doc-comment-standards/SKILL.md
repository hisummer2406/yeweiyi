# 文档与代码注释约束

## 一、实事求是（文档和注释都适用）

1. **先核对代码再写**。每条结论都要能在当前代码里找到依据，写明 `文件:行号` 或类名/方法名。不凭记忆、不照抄旧文档、不照搬 issue/审核意见里的描述——它们可能已经过时。
2. **区分"已验证"和"推断"**。只经过编译/单测的写"单测通过"，没上过真机的写"未经真机验证"；读代码推出来但没跑过的写"推断"。不写"已完成""没问题"这类没有证据的结论。
3. **日期写绝对日期**（`2026-10-06`），不写"今天""上周"。引用跨仓库代码时写明对方仓库和提交号。
4. **发现文档与代码不一致**，以代码为准改文档；拿不准是代码错还是文档错，先问用户，不要两边都猜。

## 二、按严重程度划分（问题清单、待办、审核报告）

| 级别 | 含义 | 例子 |
|---|---|---|
| **高** | 数据丢失/错误、安全问题、崩溃或 ANR、老设备升级后不可用 | 出入库记录被覆盖、凭据明文、UI 线程阻塞 |
| **中** | 功能缺失或行为与预期不符，但有绕行办法、不丢数据 | 报警恢复不上报、配置改后要重启才生效 |
| **低** | 体验、性能、代码重复、文案等 | 重复解析 JSON、注释过期 |
| **待确认** | 需要真机、产品或跨仓库确认，暂无法定级 | 负温度编码、单位量纲 |

- 清单按"高 → 中 → 低 → 待确认"排列，每条标明级别。
- 已修复的标"已修复"并写修复提交号；决定不修的写"暂不修"和一句理由。

## 三、文档要简洁

- **只写核心**：问题是什么、影响什么、怎么修/现状如何。不写排查过程、推理链、"之前以为……后来发现……"。
- **优先用表格和短句**，一条一行；同一件事只在一处详写，其他地方引用章节号。
- **不堆细节**：不贴大段代码，不列测试用例名，不复述提交信息。确有必要的代码只贴关键几行。
- **更新而不是追加**：内容变了就改原文，不在后面追加"更新：……"。版本说明每版一行。

## 四、代码注释

1. **最多 4 行**（含 `/** */` 内的文字行，不含 `@param`/`@return` 这类标签行）。写不下说明该放进文档或提交信息，注释里只留结论。
2. **写"为什么"，不写"做了什么"**：代码本身能看出来的不写；只写不看注释就会被误改的约束、坑、取舍。
3. **不写历史**：不写"之前是……""PR #38 第四轮审核……""2026-09 修复"。历史放提交信息。
4. **实事求是**：注释里的格式、单位、调用方、线程等事实必须和代码一致（例如方法名带 `ss` 但实际只到分钟，就要写清楚）。

## 五、改代码时同步更新注释和文档

每次改动代码，提交前做这几步：

1. 对改动涉及的类名、方法名、字段名、常量值，用 `git grep -F "<名字>"` 逐个搜索（不要用 `\|` 或 `\b`，本仓库的 `git grep` 会静默漏掉），检查引用它的注释和 `docs/`、`CLAUDE.md` 是否还成立。
2. 删除的方法/字段，确认没有注释或文档还在描述它。
3. 行为变了（时序、格式、线程、默认值），改掉描述旧行为的注释；超过 4 行的顺手压缩。
4. 文档里的测试数、提交号、版本号等数字要跟着改。

## 六、提交前自查

- [ ] 每条结论都有代码依据，验证程度写清楚了
- [ ] 问题清单已标严重程度并排好序
- [ ] 文档里没有排查过程和重复内容
- [ ] 新增和改动的注释都不超过 4 行，没有写历史
- [ ] 已搜索改动涉及的名字，过期的注释和文档都已更新
