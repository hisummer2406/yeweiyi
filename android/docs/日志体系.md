# 日志体系

> 来源：OpenSpec change `add-app-log-system`（2026-10-17）。编译和 JVM 单测通过，**未经真机验证**。

## 1. 结构

| 位置 | 作用 |
|---|---|
| `logic/applog/`（纯逻辑，JVM 单测覆盖） | 格式、脱敏、重复合并、级别策略、切分封顶、写线程、打包；以及领域日志用到的判定/限频/缓冲组件（`TempAnomalyDetector`、`KeyedRateLimiter`、`FrameRing`、`ProbeCommStats`） |
| `applog/AppLog` | 门面：写日志、级别设置与持久化、导出、清空 |
| `applog/ProbeLog` | 领域日志：探头通讯（PROBE 模块） |
| `applog/AlarmLog` | 领域日志：报警产生/恢复、手动解警（ALARM 模块） |
| `applog/SoundLightLog` | 领域日志：声光开启/关闭（ALARM 模块） |
| `applog/LogExportUi` + 高级设置底栏「导出日志」 | 点击直接导出；长按进入 `fragment/LogSetFragment`（日志诊断页：开关、级别 E/W/I/D、清空，给技术支持用） |

全部是 Kotlin。初始化在 `MyApplication.onCreate()` 最前面（`AppLog.init` + `ProbeLog.start`）。

## 2. 以后新增日志怎么做

| 情况 | 做法 |
|---|---|
| 零散的一两条（某处失败、某个状态变化） | 直接调用 `AppLog.e/w/i/d(模块, 事件名, key, value, ...)` |
| 一个业务领域有多处日志，或者需要状态（限频、缓冲、计数、跟上一次比较） | 在 `applog/` 下新建 `XxxLog`（`object`，对 Java 用 `@JvmStatic`），把"记什么、记哪一级"集中在里面；业务代码只调一个方法，例如 `AlarmLog.onAlarmRaised(alarm)`。方法体包在 `logSafely {}` 里，日志出错不能影响业务 |
| `XxxLog` 里有判定或计算逻辑 | 抽到 `logic/applog/`，写 JVM 单测（参考 `TempAnomalyDetector`） |
| 需要单独的文件和容量 | 在 `LogModule` 加一个值并给出模块上限；所有模块上限之和不要超过 200MB |

约定：
- 业务事件一律走级别策略，重要的记 E（默认级别是 W，E 一定会记）。`AppLog.critical` 是 `internal`，只给日志体系自己用（会话头、级别变更、导出、清空），崩溃走 `AppLog.crashSync`
- 每一轮轮询都会触发的日志只能用 D；高频路径上拼内容代价大时，先判断 `AppLog.isLoggable(模块, 级别)`
- 新增 `XxxLog` 时，在本文档 §6 补一张表，写清每条事件的级别

## 3. 怎么写一条日志

```java
AppLog.w(LogModule.PROBE, "温度异常", "pos", pos, "raw", raw);
AppLog.e(LogModule.SYSTEM, "导出失败", throwable, "path", path);
```

- 文件行格式：`2026-10-17 14:30:05.123 [PROBE][W] 温度异常 pos=3 raw=65520`，时间、模块、级别标记由日志体系生成
- 键名含 token/password/secret/pwd 的值会被掩成 `***`，但不要依赖它，凭据本来就不该写进日志

## 4. 级别约定

| 级别 | 记什么 | 估计量（推断，待真机核对） |
|---|---|---|
| E | 失败、异常；报警产生与恢复 | 平时很少 |
| W | 异常数据、异常状态 | 正常不到 1MB/天 |
| I | 状态变化、定时摘要 | 约 0.5MB/天 |
| D | 逐次收发的明细 | 约 50–60MB/天 |
| 系统关键事件 | 崩溃、会话头、级别变更/到期、导出、清空 | 不受级别限制，立即 fsync |

估算前提（推断，待真机核对，task 6.4）：每罐每轮发 45、44 两次请求，一轮约 0.3–0.4 秒，全部罐合计约 2.8 帧温度应答/秒、5–7 次收发/秒。W 级下一次 5 分钟、4 个罐的误报约 0.2MB；极端情况（某根探针整天每帧都在跳）这根探针约 15MB/天，由 PROBE 80MB 上限兜底。D 级 24 小时到期前约写 60MB，PROBE 80MB 能完整保留。

生效级别：默认开启、记 W；在日志诊断页可改为 E/W/I/D，关闭「日志记录」开关后只记 E，重新打开回到 W；选 D 时 24 小时后自动退回 W。设置持久保存在 SharedPreferences `app_log_settings`，重启不变。ERROR 级别写入后也立即 fsync。

## 5. 存储参数和模块限额

目录 `filesDir/logs/`，文件名 `<模块>-yyyyMMdd-HHmmss-NN.log`。单文件 2MB；保留 30 天；剩余空间低于 200MB 时暂停写入。参数在 `LogConfig`/`LogModule`。

| 模块 | 上限 | 当前写入方 | 依据（日志量均为推断） |
|---|---|---|---|
| PROBE | 80MB | `ProbeLog` | 唯一有高频日志的模块：D 级约 50–60MB/天，24 小时到期前约 60MB，80MB 能完整留住；W/I 级每天 1MB 以内，30 天约 30MB |
| ALARM | 30MB | `AlarmLog` | E 级一条约 200B，按（罐位，类型）10 分钟限频，每天上千条也只有约 0.2MB，30 天保留期会先到 |
| SYSTEM | 30MB | `AppLog`（会话头、级别变更、导出、清空）、崩溃 | 每次启动一条会话头，崩溃一条带堆栈约 5–10KB，量很小 |
| CLOUD | 30MB | 暂无 | 预留给 ThingsBoard 连接/RPC 日志 |
| STOCK | 30MB | 暂无 | 预留给出入库判定日志 |
| 合计 | 200MB | | 用户定的总上限；各模块上限加起来正好 200MB |

- 上限是"最多占多少"，不是预先占用：模块没写日志就不占空间
- 超限时删的是该模块最旧的整个文件（2MB 一个），新建文件时会为它预留一个文件的空间，所以写满后也不会超过上限
- 总上限 200MB 另外单独检查：以后加模块却忘了调整各模块上限，总量也不会超
- 新增模块时，从现有模块里匀出上限，保持合计不超过 200MB；高频模块（有 D 级逐帧日志的）给大份额，低频模块 10–30MB 足够

## 6. 现有领域日志

**`AlarmLog`（ALARM 模块）**

| 事件 | 级别 | 说明 |
|---|---|---|
| `报警产生` | E | 所有报警类型（高温除外）；液位类报警和探头断线另附带最近报文。只有探头断线 `PRO_ERR_CONN` 按罐位 10 分钟限频（断线期间每轮轮询都会触发）；其他类型只在状态切换时触发，每次都记 |
| `高温报警` / `高温恢复` | E | 带阈值和补偿；报警时若 PROBE ≤ W，附带该罐最近报文（规则见下方「最近报文」）。只有记过「高温报警」的罐才记「高温恢复」：本地标志 `isTemperAlarm` 在开机和手动解警时都会被置 false，不能当成"正在报警" |
| `手动解警` | E | 主界面"解警"按钮，记下当时在报警的罐和 `alarmState`；解警只消声光，不当作恢复 |

**`SoundLightLog`（ALARM 模块）**

| 事件 | 级别 | 说明 |
|---|---|---|
| `声光开启` | W | `by=高液位/低液位/高水位/高温`，在 `AlarmDetection` 调 `openHeightAlarm`/`openLowOilAlarm` 之前记 |
| `声光关闭` | W | `branch=` 是哪类报警恢复触发的；`stillAlarming=` 是关铃那一刻其他仍在报警的罐（`罐位(state=alarmState)`）。铃是全局一个开关，这一项不为空就说明别的罐的铃被一起关了。开机第一轮会有约"罐数×3"条，属正常 |

**`ProbeLog`（PROBE 模块）**

| 事件 | 级别 | 说明 |
|---|---|---|
| `温度异常` | W | 45 帧跳变 ≥5℃、进入/离开超阈值、地址匹配不到罐；随后附带最近报文 |
| `最近报文` | W | 温度异常、高温报警、液位类报警、探头断线时写出。**增量**：只写该罐上次写出之后的新帧（最多 30 帧，约 10 秒），首行 `since=` 是上次写到的时间，接着上一份读就是完整时间线；`count=0` 表示和上一份相同，`gap=true` 表示中间有帧已被挤出缓冲。每罐每 10 分钟最多 10 次，超出记 `skipped=N`；一份约 3KB，最坏约 4MB/天/罐 |
| `温度首读` / `通讯摘要` | I | 每次启动每罐第一帧；每 5 分钟每罐 ok/bad/noResp 计数 |
| `收发` | D | 每一次收发：罐位、请求类型、结果、原始 hex（45 帧的温度可由 hex 解出，不再单独记一行） |

跳变阈值 5℃ 是推断值（`TempAnomalyDetector.DEFAULT_JUMP_THRESHOLD`），现场数据回来后按实际调整。

## 7. 现场使用

1. 默认已经在记 W，现场不需要任何设置。需要更详细的日志时，长按高级设置底栏的「导出日志」进入日志诊断页，选 I 或 D（D 24 小时后自动退回 W）
2. 等问题复现
3. 在高级设置页点「导出日志」，在外部存储根目录得到 `yeweiyi-log-<设备编号>-<时间>.zip`（含各模块原始文件 `logs/`、按时间合并全部模块的 `all.log`、`crashLog/`、`device-info.txt`；分析时一般直接看 `all.log`），拷出发回。每次导出会先删掉根目录里旧的 `yeweiyi-log-*.zip`，只保留最新一份，避免占满分区导致日志暂停写入
