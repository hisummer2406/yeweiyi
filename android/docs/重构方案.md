### 阶段 1 — 织网（1–2 周）★ 整个方案的前提

给 26 个纯 JVM 类补单元测试，重点两块：

- **`CRCheck`（1494 行）** — 校验算法，输入输出明确
- **`factory/` 各厂商协议解码** — `LDCompany` / `LD2Company` / `ZhongChengCompany` / `VR350Factory`

**做法**：把现场抓到的真实报文存为 fixture 字节数组，断言解析出的液位/温度值。**本阶段不修改任何生产代码**，纯增量。

**为何必须排在架构调整之前**：后续每一次搬动代码，都要靠这张网确认"协议解析仍然正确"。没有它，重构等同于拿现场设备做赌注。

**风险：零**（只增不改）。

> 起步产物见 `app/src/test/java/com/sansen/yeweiyi/utils/CRCheckTest.java`。

---

### 阶段 2 — 确立两条边界（2–3 周）

**数据边界**：当前 8 个 UI 文件直接调用 `DBDataManager`（59 个 public 方法的大杂烩）。按领域拆分为 4 个 Repository——油罐、出入库、报警、交班——UI 仅依赖 Repository 接口。

**硬件边界**：将 `SerialPortManager` 正式确立为 HAL，立规矩：UI 层不得直接调用，一律经由上层 Manager。它目前已无 UI 依赖，重点是防止腐化。

**风险：中**，阶段 1 的测试网可覆盖协议部分。

---

### 阶段 3 — 拆解 `MainActivity`（2–3 周）

966 行，同时承担定时轮询、Fragment 导航、报警响应、密码校验、出入库业务动作、触摸分发。拆分为导航器 + 报警协调器 + 轮询器 + 业务动作四部分。

> ### ⚠️ 编译期无法发现的地雷
>
> 布局文件中有 **18 处 `android:onClick="but_xxx"`**，通过字符串反射绑定到 `MainActivity` 的方法。
>
> **把这些方法搬走，编译完全不报错，用户点击时才崩溃。**
>
> 正确顺序：
> 1. 先将 18 处 `android:onClick` 全部改为代码中的 `setOnClickListener`，使引用关系变为编译期可见
> 2. **然后**再搬移方法
>
> 顺序颠倒会在现场出事故。

**风险：高**，建议逐方法搬移 + 每次手工回归。

---

### 阶段 4 — 错误处理（穿插进行）

178 处 `printStackTrace()` 不要一次性全改。按链路优先级推进：

**串口通信 → CRC 校验 → 数据库写入**

让异常接入 `AlarmManager` 上报，而非消失在日志中。对无人值守设备而言，"静默错误"比崩溃危险得多——崩溃至少有 `CrashApphandler` 兜底记录并重启。

**风险：低**。

## 四、明确不建议做的事

这部分与上文同等重要——以下都是常见的"正确答案"，但在本项目中是陷阱。

### ❌ 不要升级 targetSdk（27 → 29+）

项目中有 **17 处 `Environment.getExternalStorageDirectory()`**，支撑着崩溃日志、Excel 导出、`UploadHandler`、`DownloadHelper`、USB 挂载。升级到 29+ 触发分区存储后，这 17 处会集体失效，且往往在现场才暴露。

本设备不上应用商店，没有升级的外部压力。**保持 27 是理性权衡，不是偷懒。**

### ❌ 不要迁移 AndroidX

`app/libs/` 中 22 个本地 jar 在编译期依赖 support 库，jetifier 对本地 jar 的转换不可靠。工作量以月计，功能收益为零。

### ❌ 不要替换 xUtils ORM / 重写为 MVVM / 引入 Kotlin·Compose

数据层已是全项目最健康的部分（仅 3 个文件碰 DB），改动它是负收益。MVVM 模板在上一轮已被抛弃过一次。

## 四点五、阶段 4 中发现的两处缺陷（均**未修复**，需产品/硬件侧判断）

### 4.5.1 报警上报存在三层静默失败，且方法谎报成功 ⚠️

`service/BackService.java` 的上报链路：

```java
public void publish(MqttTopic topic, MqttMessage message) throws ... {
    if (client.isConnected()) {     // ① 断连时静默丢弃，不抛异常、不重试
        topic.publish(message);
    }
}

private boolean sendAlarms(String msgInfo) {
    try {
        publish(topic, message);
    } catch (MqttPersistenceException e) {   // ② 异常被吞
    } catch (MqttException e) {              // ②
    }
    return true;                              // ③ 失败也返回 true
}
```

`sendAlarms` / `sendUnloadOils` 经 AIDL 接口 `IBackService.sendAlarm()` 暴露给**跨进程调用方**，
该调用方会把 `true` 理解为"报警已送达服务器"。

实际后果：设备断网或 MQTT 异常时，**报警数据被丢弃且无人知晓**。对液位监测设备而言这是安全相关缺陷。

本轮已做（不改行为）：补齐 ②的日志，并在 ①的丢弃分支加 `Log.w`，使丢弃在现场日志中可见。

待决策（属行为变更）：
- `sendAlarms` 失败时应返回 `false` —— 但会改变 AIDL 调用方看到的结果，需确认调用方如何处理失败
- 断连时是否应入队重发而非丢弃

### 4.5.2 探头协议分发缺少 break，LD 结果被 LD2 覆盖 ⚠️

`manager/SerialPortManager.java` 的 `switch (mOilCan.getProbeType())`：`case 1`（LD 探头）
末尾**缺少 `break`**，执行穿透到 `case 2`，`isRight` 被 LD2Company 的解析结果覆盖。
`case 0` 与 `case 2` 均有 `break`，也无 fall-through 注释，判断为漏写。

代码中已标 `FIXME`，**未修改**：补 `break` 会改变现场设备读数行为。
若现场 LD 探头一直读数正常，需先查明原因（可能存在巧合性兼容），再决定是否修复。

## 五、CRC 相关的两处 API 陷阱（阶段 1 中发现）

以下**均非线上故障**，但都是"下一个调用者容易踩中"的坑，已在 `CRCheckTest` 中用测试固化：

### 5.1 `getModBusCRC()` 返回值不补零

```java
return Integer.toHexString(CRC);   // CRCheck.java:995
```

CRC 高位为 0 时返回长度不足 4 的字符串。最常见的 Modbus 读保持寄存器报文 `01 03 00 00 00 01` 的 CRC 为 `0x0A84`，此处返回 **`"a84"`（3 位）**。

当前唯一调用点 `LDCompany.java:72` 用自带的 `getString()` 补零兜住了，因此暂无故障。风险在于：**正确性依赖每个调用者都记得补零**。

### 5.2 `crc16()` 与 `crc162()` 仅字节序不同

两者算法完全一致，只有最后一行返回顺序相反：

| 方法 | 返回格式 | `"123456789"` 的结果 |
|---|---|---|
| `crc16()` | `%02X%02X`(high, low) | `"4B37"` |
| `crc162()` | `%02X%02X`(low, high) | `"374B"` |

命名无法体现差异，调错不会报错、只会静默算出错误校验值。此外 `getModBusCRC()` 返回**小写**，另两个返回**大写**（`Byte.decode` 能容忍大小写，故当前无故障）。
