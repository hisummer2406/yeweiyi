# 液位仪 App 重构方案 v2

> 适用范围：`com.sansen.yeweiyi`（安卓液位仪）
> v1 撰写于 2026-07-31，v2 改写于 2026-08-13
> v1 全文见 git 历史（`git show 001af0a:docs/重构方案.md`）

---

## 零、为什么有 v2

v1 执行到 2026-08-13 的实际结果：**阶段 0、1、4 完成或部分完成，阶段 2、3 转成 OpenSpec change 后 0/106 任务，停滞 5 天。**

停滞不是执行力问题，是方案本身的问题。v1 有一个没被说破的前提——**假设「补上单元测试」这件事是可以先做完再动结构的**。实际不成立：最值得测的 `factory/` 协议解析，9 个文件里 6 个 import 了 `android.*`，纯 JVM 跑不起来。想测它必须先改结构，想改结构又缺测试保护。v1 把这个死锁记为「阶段 1 的一处修正，顺延至阶段 2」，但它其实是整个方案排序的失效点。

### v2 与 v1 的主要差异

| 决策项 | v1 | v2 | 理由 |
|---|---|---|---|
| 首要目标 | 补测试 → 分层 → 拆 UI | **先建立可验证性** | 本机验证不了硬件行为，不解决这点，后续每次改动都是赌博 |
| 测试策略 | 给纯 JVM 类补单测 | **录制真机报文做 golden master** | 手写断言只能覆盖已知场景；录制能覆盖现场真实工况 |
| 切分方式 | 横切（先全部分层，再全部拆 UI） | **竖切**（一个模块走完全流程，再下一个） | 横切产生长命分支，无 CI 的单人项目合不回去 |
| 重构判据 | 朝「架构正确」 | **朝「可测性」** | 不增加可测面的结构改动一律推迟 |
| 缺陷处理 | 记录待决策（四点五） | **排在所有重构之前** | 这是油罐报警设备，读数错误是安全问题 |
| 包结构整理 | 阶段 2 含包名规范化 | **砍掉** | 零功能收益、毁 blame，且有约 7000 行是三方 vendored 代码 |

## 一、四条指导原则

后面所有排序都由这四条推出，遇到分歧时回来对照这四条。

### 1. 瓶颈是验证能力，不是代码质量

本机 `assembleDebug` 通过只证明能编译。串口协议、探头解析、报警触发——系统真正的核心资产，在办公室一行都验证不了。

**推论**：任何提升「我能否知道自己搞坏了」的动作，优先级高于任何提升「代码好不好看」的动作。

### 2. 重构方向朝可测性，不朝整洁

每次动手前问一句：**这次改完，是不是有新代码能在 JVM 上跑测试了？**

- 是 → 做
- 否 → 推迟，无论它多「应该」做

### 3. 竖切，不横切

不要「先把所有模块分层，再给所有模块补测试」。而是锁定一个模块，在里面走完 **抽纯逻辑 → 补测试 → 重排结构 → 装机验证** 的完整循环，然后换下一个。

**推论**：每个提交都能单独装到设备上跑。不开长命重构分支。

### 4. 已知缺陷优先于架构改进

现有两个已定位、未修复的缺陷（见第八节）都影响读数或报警送达正确性。在一台无人值守的油罐监测终端上，这比任何架构问题都紧急。

## 二、硬约束

v1 的三条仍然成立，v2 补两条：

1. **设备部署在客户现场**，回归成本极高 → 不做大爆炸重写
2. **本机零硬件验证能力** → 必须先造出替代验证手段（v2 新增，替代 v1 的「零测试网」）
3. **核心资产是硬件协议，不是 UI** → 优化优先级要倒过来
4. **单人开发、无 CI** → 长命分支必然烂尾，改动必须小步可合（v2 新增）
5. **约 14% 的代码是三方 vendored** → 不在重构范围内（v2 新增）

## 四、执行路线

```
第 0 步  修已知缺陷 ──┐
                      ├─→ 第 1 步 建 golden master ──→ 第 2 步 factory/ 竖切样板 ──→ 第 3 步 复制样板
第 -1 步 外部接口加固 ┘        （唯一需要现场）              （验证方法本身）         （其余模块）
                                                                                            │
                                                                                            ↓
                                                                                    第 4 步 拆 MainActivity
```

### 第 -1 步 — 外部接口加固（可并行，不依赖现场）

`openspec/changes/harden-device-external-access` 的 §1 MQTT 凭据外置，是四个 change 里唯一**完全不碰硬件行为**的部分。它可以在等待现场机会的时候并行做掉。

密钥轮换也在这里——v1 阶段 0 只做了「外置」，**凭据至今未轮换**，旧值仍在 git 历史里，等同已泄露。

**风险：低。验证：本机编译 + MQTT 连通性。**

### 第 0 步 — 修两个已知缺陷（需硬件侧确认）

见第八节。两个都是一行到几行的改动，但都需要先向硬件/产品侧确认现场实际情况：

- **4.5.2 缺 `break`**：需确认现场是否真有 LD 与 LD2 两种探头共存。若只部署了一种，此缺陷当前无实际影响，可降级；若共存，则现在的 LD 读数是错的，必须立即修。
- **4.5.1 报警谎报成功**：需确认 AIDL 调用方拿到 `false` 会如何处理，才能决定改返回值还是加重发队列。

**这一步的产出可能是「确认无需修改」，那也是有效产出。** 不确认就往下走，等于把一个已知的正确性问题带进整轮重构。

### 第 1 步 — 建立 golden master（★ 关键路径，唯一需要现场）

这是整个 v2 的支点。目标：**把「不可验证」变成「可验证」。**

#### 做法

在 `SerialPortManager` 的两个接缝上加一个可开关的录制钩子：

| 接缝 | 位置 | 录什么 |
|---|---|---|
| 输入 | `RequestThread.run()` 中 `data = bytesToHexString(...)` 之后、分发给 `probeInfoPase` 之前 — `SerialPortManager.java:265` 附近 | hex 报文 + 时间戳 + 探头类型 + 油罐位 |
| 输出 | `IParseDataListener.hexDataParseFinish(OilCan)` — `SerialPortManager.java:418` | 解析出的 `OilCan` 全字段快照 |

> **2026-08-14 更正**：本表最初写的输入接缝是 `ProbeReciveDataListener.reciveData(byte[])`（`:339`），**是错的**——
> 那条路径无人实现、恒为 `null`，且进入即 NPE（已登记为 8.3）。真正的输入接缝在 `:265` 附近。
>
> 另外录 **hex 字符串**而非上游的原始 `byte[]` 是有意为之：`probeInfoPase(String, IParseDataListener)` 吃的就是它，
> 将来抽出的 `XxxParser` 吃的也是它，录在这一层才能保证「重放时喂进去的」与「现场当时喂进去的」是同一个东西。
>
> **覆盖范围**：只覆盖探头轮询路径的三种 `probeType`（0 中诚 / 1 LD / 2 LD2）。`VR350Factory` 是 `PCDataFactory`，
> 走 PC 通信线程，不经这条路径也不回调 `hexDataParseFinish`，本轮不覆盖。

录制开关默认关闭，通过设置页或 `local.properties` 注入的 `BuildConfig` 标志启用，落盘到 `/sdcard/`。

#### 现场采集要求

- 正常工况跑满一天（覆盖昼夜温差，温度字段能拿到有意义的范围）
- 尽量制造报警工况（高位、低位、探头断线）
- **每种在用的探头型号都要采到**——这决定了 golden master 的覆盖面

#### 回来之后

把采集到的 `(字节帧 → OilCan)` 配对变成 JVM 上的重放测试：喂进同样的字节，解析输出必须逐字段一致。

> 这是 characterization test（特征化测试）——不问「代码应该输出什么」，只锁死「代码现在输出什么」。接手别人的代码时，你没有资格问前一个问题。它的价值不在于证明代码正确，而在于**任何后续改动一旦改变了行为，会立刻红**。

#### 风险与前置条件

**这一步是整个方案的单点依赖。** 如果短期内拿不到现场机会：

- **降级方案**：从现有 `factory/` 代码和厂商协议文档反推构造报文，手写 fixture。覆盖面差得多（只能覆盖你想得到的场景，覆盖不了现场的畸形帧、时序异常），但聊胜于无。
- **不可接受的方案**：跳过这一步直接重构 `factory/`。

**风险：低（只增不改）。验证：本机。**

---

### 第 2 步 — `factory/` 竖切（验证方法本身）

有了 golden master 才能做这一步。选 `factory/` 打头阵的三个理由：

1. 它是全仓库最值得测的代码——协议解错等于读数错
2. 它同时卡住了「规范结构」和「补测试」两件事
3. 它本质是纯函数，抽出来风险低

#### 顺序

1. 把纯解析逻辑从 6 个 import `android.*` 的类里剥出来，成为不依赖 Android 的类
2. golden master 重放测试改为直接打在新抽出的纯逻辑上
3. 原类退化为薄适配层（负责 `Context`/`SparseArray` 那部分）
4. 装机验证一轮

#### 这一步的真正产出

不是「`factory/` 变干净了」，而是**一个可复制的模板**，以及**一个真实的耗时数据**。拿这个数字去重排剩下的工作量，比现在拍脑袋估准得多。

**风险：中。验证：golden master 重放 + 装机回归。**

---

### 第 3 步 — 复制样板到其余模块

按扇入面从小到大推进，每个模块一个完整循环：

| 顺序 | 模块 | 扇入 | 备注 |
|---|---|---|---|
| 1 | 交班（ShiftRepository） | 最小 | 先验证模板在数据层是否同样适用 |
| 2 | 出入库（StockRepository） | 中 | |
| 3 | 报警（AlarmRepository） | 中 | 与第 -1 步的报警上报加固有交集，注意别撞车 |
| 4 | 油罐（OilTankRepository） | 最大 | 放最后 |
| 5 | 删除 `DBDataManager` | — | 前四步做完的自然结果，不单独规划 |

这一段对应 `openspec/changes/layer-data-and-hardware-boundaries` 的 **§3–§7**（重排后编号），**每一节内部按竖切模板执行**（先补该领域的测试，再搬代码）。

**风险：中。验证：每个 Repository 自带测试 + 装机回归。**

### 第 4 步 — 拆解 `MainActivity`

放到最后，因为它是**唯一一段无法用 golden master 保护的重构**——UI 交互没法录制重放。

⚠️ **不可跳过的前置**：`android:onClick="but_xxx"` 是字符串反射绑定。把这些方法搬走**编译完全不报错，用户点击时才崩溃**。

**2026-08-13 复核：这个雷比 v1 记的更大。** v1 写的「18 处」是**去重后的方法名数**，实际绑定点有 **34 处**，而且分布很危险：

| 布局 | 绑定数 | 说明 |
|---|---|---|
| `activity_main.xml` | 14 | 直觉之内 |
| 8 个 `fragment_*.xml` | 19 | ⚠️ **在 Fragment 布局里，但方法定义在 `MainActivity`** |
| `activity_login.xml` | 1 | 死布局，见下 |

Fragment 布局里的 `android:onClick` **不解析到 Fragment，解析到宿主 Activity**。已抽查确认 `bar_but_alarm`、`but_startJiaoBan`、`btn_jieJing`、`btn_kuCunRecord`、`main_but_set` 全部定义在 `MainActivity`。

这意味着：**超过一半的绑定，其 XML 文件和目标方法根本不在同一个类的视野里。** 拆 `MainActivity` 时，只盯着 `activity_main.xml` 会漏掉 19 处，而这 19 处崩在各个业务页面（交班、出入库、报警、库存），比主界面更难在自测中覆盖到。

正确顺序：

1. 先把 **34 处**（含 fragment 布局那 19 处）`android:onClick` 全部改为代码里的 `setOnClickListener`，让引用关系变成编译期可见
2. **这一步单独提交，绝不与拆分混在一起**
3. 然后才逐个搬移方法，每次手工回归

> **顺带发现**：`activity_login.xml` 未被任何 Java 代码和 `AndroidManifest.xml` 引用，且其 `android:onClick="login"` 指向的方法**全项目不存在**。这是个死布局，可删（已用 `grep -F` 双向验证）。

**风险：高。验证：只能靠手工回归，逐方法搬移。**

## 五、砍掉与推迟的

v1 及 OpenSpec 里的 106 个任务，v2 明确处置如下。**这一节是 v2 的主要价值之一——不做什么和做什么同样重要。**

| 项目 | 处置 | 理由 |
|---|---|---|
| 把 38 个顶层包文件挪进 `com.sansen.yeweiyi` | **砍掉** | 零功能收益、全部风险、毁掉 `git blame`；且其中含三方 vendored 代码，改它是净负债 |
| `utils/` 47 文件重新归类 | **推迟到最后** | 同上。等所有模块竖切完，剩下的自然会归位 |
| 两个同名 `BaseFragment` 合并 | **降级为顺手做** | 死代码删掉即可，不值得单列任务 |
| `layer-data` 硬件边界去 UI 依赖（原 §6 → 现 **§8**）| **保留，移到全部 Repository 之后** | 需真机验证刷新时序，无法用重放测试覆盖；且它改的接缝正是录制钩子所挂位置，放后面免得调两次 |
| `layer-data` `factory/` 纯解析抽取（原 §7 → 现 **§2**）| **提到最前** | 它是死锁的钥匙，原计划把它排在 34 个任务的最末尾是排序错误 |
| golden master 录制与采集（原**不存在**）| **新增为 `layer-data` §1** | 原 §7.2 直接假设「现场抓取的真实报文」已存在，却没有任何任务产出它 |
| `device-write-back-sync` 全部 | **排在 Repository 之后**（2026-08-15 修订）| 原为「推迟到重构后」。产品侧确认远程客户端读写都要（issue #4 决策 1），它已成为需求 B 的必做项，不再无限期推迟；但仍需排在 `layer-data` §3/§4 之后 —— 否则 §2 的持久化方法写在 `DBDataManager` 上，注定返工 |

> **OpenSpec 已同步（2026-08-13）**：以上调整均已落到 `openspec/changes/`，四个 change 全部通过 `validate --strict`。
> 任务总数 106 → 121（`layer-data` 34→48，新增 golden master 任务组；`split-main-activity` 24→25）。
> 具体落点：`layer-data` 的 tasks.md 重排 + design.md 迁移顺序改写 + `protocol-parser-testability` spec 新增两条 requirement；
> `split-main-activity` §1 补 fragment 布局分布；`device-write-back-sync` tasks.md 顶部加暂缓横幅（任务内容未改，可随时恢复）。

## 六、提交与验证纪律

这几条都是这个仓库已经吃过亏才写下来的：

1. **机械改动与语义改动永不同一个 commit。** CRLF 统一那次动了 410 个文件，导致 `MD5utils.java` 一行 `catch` 修改显示成 `32+/31-`。`split-main-activity` §1 特意标注「不可与拆分混在一起提交」也是这个原因。
2. **每个 commit 都能单独装机运行。** 无 CI 的单人项目，分支活过两周就再也合不回去。
3. **删任何东西前用 `git grep -F` 逐词验证。** 本环境 `git grep` 的 `\|` 和 `\b` 会静默匹配为空并返回 0——最坏的失败模式。已经因此删掉 `R.string.apkurl` 搞挂过一次构建。
4. **`testDebugUnitTest` 报 `UP-TO-DATE` 时不算通过。** 用 `./gradlew :app:cleanTestDebugUnitTest :app:testDebugUnitTest`，或读 `app/build/test-results/testDebugUnitTest/*.xml`。
5. **凡涉及串口/探头协议的改动，本机绿了也不算完，必须装机。**

## 七、明确不做的事

v1 的三条 ❌ 全部保留，v2 补两条。

### ❌ 不要升级 targetSdk（27 → 29+）

21 处 `Environment.getExternalStorageDirectory()` 支撑崩溃日志、Excel 导出、`UploadHandler`、`DownloadHelper`、USB 挂载。升到 29+ 触发分区存储后集体失效，且往往在现场才暴露。本设备不上应用商店，没有升级压力。**保持 27 是理性权衡，不是偷懒。**

### ❌ 不要迁移 AndroidX

`app/libs/` 中 22 个本地 jar 编译期依赖 support 库，jetifier 对本地 jar 转换不可靠。工作量以月计，功能收益为零。

### ❌ 不要替换 xUtils ORM / 重写为 MVVM / 引入 Kotlin·Compose

数据层是全项目最健康的部分（仅 3 个文件碰 DB）。MVVM 模板在上一轮已被抛弃过一次。

### ❌ 不要碰 JNI 层和 vendored jar（v2 新增）

`app/libs/` 里的 SDK 大多没有 Maven 版本，配套特定硬件。`cpp/` 下的 serialport / atg / bspatch 同理。

### ❌ 不要追求「架构正确」（v2 新增）

### 8.1 报警上报三层静默失败，且方法谎报成功 ⚠️

`service/BackService.java`：

```java
public void publish(MqttTopic topic, MqttMessage message) throws ... {
    if (client.isConnected()) {     // ① 断连时静默丢弃，不抛异常、不重试
        topic.publish(message);
    }
}

private boolean sendAlarms(String msgInfo) {
    try {
        publish(topic, message);
    } catch (MqttPersistenceException e) {   // ② 异常被吞
    } catch (MqttException e) {              // ②
    }
    return true;                              // ③ 失败也返回 true
}
```

`sendAlarms` / `sendUnloadOils` 经 AIDL 接口 `IBackService.sendAlarm()` 暴露给**跨进程调用方**，该调用方会把 `true` 理解为「报警已送达服务器」。

**实际后果：设备断网或 MQTT 异常时，报警数据被丢弃且无人知晓。** 对液位监测设备而言这是安全相关缺陷。

已做（不改行为）：补齐 ② 的日志，并在 ① 的丢弃分支加 `Log.w`，使丢弃在现场日志中可见。

待决策（行为变更）：失败时返回 `false`（需确认 AIDL 调用方如何处理失败）；断连时是否入队重发。

| **存在 `probeType=1`** | **该油罐当前读数就是错的** | 优先级最高，需评估历史数据可信度后再修 |

### 8.3 `ProbeReciveDataListener` 是死代码，且其调用点必 NPE ⚠️

（2026-08-14 实施 v2 第 1 步时发现，**仅登记未修**）

### 8.4 LAN 登录接口接受出厂默认口令 `admin`/`admin` ⚠️

（2026-08-14 实施 MQTT 凭据外置时顺带发现，**仅登记未修**）

未修原因（属行为变更，需产品侧决定）：
- 现场设备是否已经在用这组默认口令登录？直接改会把操作员挡在门外
- 应该改成「首次启动强制修改口令」，还是「出厂时逐台写入随机口令」？前者要加 UI 流程，后者要改产线

## 九、CRC 相关的两处 API 陷阱

均非线上故障，但都是「下一个调用者容易踩中」的坑，已在 `CRCheckTest` 中用测试固化。

### 9.1 `getModBusCRC()` 返回值不补零

```java
return Integer.toHexString(CRC);   // CRCheck.java:995
```

CRC 高位为 0 时返回长度不足 4 的字符串。Modbus 读保持寄存器报文 `01 03 00 00 00 01` 的 CRC 为 `0x0A84`，此处返回 **`"a84"`（3 位）**。

当前唯一调用点 `LDCompany.java:72` 用自带的 `getString()` 补零兜住了。风险在于**正确性依赖每个调用者都记得补零**。

### 9.2 `crc16()` 与 `crc162()` 仅字节序不同

| 方法 | 返回格式 | `"123456789"` 的结果 |
|---|---|---|
| `crc16()` | `%02X%02X`(high, low) | `"4B37"` |
| `crc162()` | `%02X%02X`(low, high) | `"374B"` |

命名无法体现差异，调错不报错、只静默算出错误校验值。另外 `getModBusCRC()` 返回**小写**，这两个返回**大写**。
