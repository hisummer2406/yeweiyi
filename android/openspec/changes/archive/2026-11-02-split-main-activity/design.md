## Context

`MainActivity`（966行）承担导航、轮询、报警响应、密码校验、出入库业务动作、触摸分发六类职责。18 处 `android:onClick`（34 个 XML 属性引用）以字符串反射绑定到它的方法。见 proposal.md - Why。本变更假定 `layer-data-and-hardware-boundaries`（阶段2）已经或至少部分落地——报警协调器需要 `AlarmRepository`，油罐相关的业务动作需要 `OilTankRepository`。

## Goals / Non-Goals

**Goals:**
- 把反射绑定变成编译期可见的调用，消除"搬方法不报错、点击才崩溃"的地雷。
- 按职责把 966 行拆到四个协作类里，`MainActivity` 保留 Activity 生命周期与四者的组装。

**Non-Goals:**
- 不引入事件总线、依赖注入或 Fragment 通信框架——四个协作类通过 `MainActivity` 持有的普通引用互相协作即可。
- 不改变任何按钮的现有业务行为，只搬职责归属，不重写逻辑。
- 不在本变更里处理 `layer-data-and-hardware-boundaries` 尚未完成的领域——若报警协调器所需的 `AlarmRepository` 还没落地，报警协调器暂时继续依赖 `DBDataManager`，待阶段2那部分完成后再补一个小任务切过去（见 tasks.md 的显式标注，不能模糊处理）。

## Decisions

**1. 先做 `onClick` → `setOnClickListener` 转换，且必须先落地、先验证，再动职责拆分。**
这不是风格偏好，是给后续拆分建立编译期保护网：拆分时如果不小心移动或改名了某个被 `onClick` 引用的方法，转换前会编译通过、点击崩溃；转换后编译器会直接报错。`docs/重构方案.md` 阶段3明确写了这个顺序不能颠倒。
*备选方案*：拆分时见招拆招，逐个确认哪些方法有 `onClick` 绑定。放弃原因：容易漏判，且没有编译器兜底，现场出事故的代价远高于先做一轮机械转换的成本。

**2. 四个协作类通过构造函数/setter 注入方式持有，不做成静态单例。**
`MainActivity` 是它们的组装者和生命周期宿主，四者本身不应该各自变成新的全局单例（否则只是把"一个上帝类"换成"四个隐藏耦合的单例"，没有解决问题）。
*备选方案*：仿照项目里已有的 Manager 模式做成单例。放弃原因：这些协作类的生命周期天然绑定 `MainActivity`（Activity 销毁重建时需要重新组装），做成单例会引入 Activity 泄漏或状态不一致的新风险。

**3. 报警协调器优先对接 `AlarmRepository`（如已就绪），否则显式保留对 `DBDataManager` 的临时依赖并加 TODO。**
不为了"看起来干净"而在阶段2完成前伪造一个还不存在的依赖。

## Risks / Trade-offs

- [风险] 18 处 `onClick` 转换本身虽是机械操作，但遗漏一处会导致该按钮完全失效（而不是崩溃，更隐蔽）→ 缓解：转换后逐个按钮做一遍真机点击回归，而不仅是编译检查。
- [风险] 触摸分发拆到导航器后，某些依赖"当前 Fragment 状态"隐式时序的代码可能出现执行顺序变化 → 缓解：拆分导航器时保持原有调用顺序不变，只做搬移不做重排；每个任务组完成后真机走一遍导航路径。
- [风险] 报警协调器与阶段2的 `AlarmRepository` 存在依赖关系，若两个变更并行推进，可能出现集成冲突 → 缓解：tasks.md 里报警协调器相关任务显式标注"依赖 layer-data-and-hardware-boundaries 第3组任务"，不满足则先用临时方案（继续依赖 `DBDataManager`）并留 TODO，不阻塞本变更其余部分。

## Migration Plan

1. 第一步且仅此一步先落地：18 处 `onClick` → `setOnClickListener`，独立提交，独立验证（含真机点击回归），确认无遗漏后才能开始职责拆分。
2. 按导航器 → 轮询器 → 业务动作 → 报警协调器的顺序拆分（报警协调器放最后，因为它可能需要等待阶段2的 `AlarmRepository`）。
3. 回滚策略：每个任务组是独立提交，出问题可单独 `git revert` 对应提交而不影响已完成的其他部分。
