## Context

见 proposal.md - Why。三块加固互相独立（LAN鉴权、MQTT凭据、报警上报诚实性），可以并行开发，放在同一个 change 里是因为它们有同一个触发原因（受众扩大到小程序/PC）且优先级相同，不是因为技术上耦合。

## Goals / Non-Goals

**Goals:**
- LAN 写接口上线前，有一个能用的最小鉴权机制。
- MQTT 凭据不再硬编码，且生产环境完成一次真实轮换。
- `sendAlarms`/`sendUnloadOils` 的返回值诚实反映投递结果，且失败不等于数据丢失。

**Non-Goals:**
- 不做完整的用户权限体系升级（`Authorization` 表的细粒度权限管理不在本变更范围，现有 13 个权限位维持原样）。
- 不引入 OAuth2/JWT 等标准协议——设备是单租户嵌入式终端，不是多租户 web 后端，标准协议的复杂度收益不成比例。
- 不解决"云端下发的写命令"的鉴权（`device-write-back-sync` 的 MQTT 写路径鉴权依赖的是 MQTT 层本身的凭据，本变更把 MQTT 凭据从硬编码改成外置就是这部分的加固，不需要在应用层再加一层）。

## Decisions

**1. LAN 鉴权用简单 token，不用 JWT。**
`/login` 校验成功后生成一个随机 token（`UUID.randomUUID()` 即可，不需要签名/加密），存一份 `token → 过期时间` 的内存映射（设备重启后需要重新登录，可接受——这是一个通常常开机的嵌入式终端，不是频繁重启的场景）。后续请求在请求头带 `X-Auth-Token`，服务端校验是否存在且未过期。过期时间给一个宽松值（比如 24 小时），因为这是运维/对接场景，不是高安全性要求的金融场景。
*备选方案*：JWT。放弃原因：JWT 的签名/刷新机制在单机、无多方验证需求的场景下是过度设计，且要引入新的 JWT 库依赖（`app/libs/` 已经堆了一大堆有版本兼容风险的本地 jar，能不加新依赖就不加，呼应 CLAUDE.md 对 `app/libs/` 的态度）。

**2. MQTT 凭据外置到 `local.properties`，照抄 `ApiConfig` 已有模式，不新建机制。**
新增 `MQTT_USERNAME`/`MQTT_PASSWORD` 两个 `BuildConfig` 常量，注入路径和 `PRODUCT_KEY` 等完全一致（`app/build.gradle` 读 `local.properties` → 注入 `BuildConfig` → `ApiConfig` 再暴露一层）。不引入新的密钥管理方案（比如 Android Keystore），因为现有四个凭据已经是这个模式，保持一致比追求"更安全"的新机制更重要——降低认知负担，且这四个凭据本来就要跟着这两个一起轮换。
*备选方案*：用 Android Keystore 加密存储。放弃原因：Keystore 主要防的是"应用被逆向后读出明文"，但这台设备的真正风险面是"MQTT broker 侧的账号密码被知道"，Keystore 解决不了这个问题，反而增加实现复杂度。

**3. 报警上报采用"诚实返回 + 本地持久化队列补投"，不是"二选一"。**
`docs/重构方案.md` 4.5.1 原本列了两个互斥选项（返回 `false` 或 入队重发）。本变更把两者合并：`sendAlarms`/`sendUnloadOils` 发布失败或断连时，**立即返回 `false`**（不再谎报成功），**同时**把这条消息写入一张新的本地表（复用现有 `DaoHelp`/`DbUtils`，不引入新的持久化机制），在 `BackService` 已有的重连检测逻辑（`onReloadMqtt`/`notifyOiline`）触发时自动补投未成功的记录，成功后从表里删除。
*备选方案A（只返回false，不做队列）*：放弃原因——网络抖动导致的报警丢失，对无人值守设备来说是不可接受的，哪怕调用方后续改成处理 `false`，也只是"知道丢了"，数据本身还是丢了。
*备选方案B（只做队列，返回值继续谎报true）*：放弃原因——`sendAlarms` 通过 AIDL 暴露给跨进程调用方，调用方基于返回值做的任何逻辑判断（哪怕现在没有）都建立在假数据上，诚实返回值是更基础的正确性问题，不应该用"反正后面会补投"来打折扣。

## Risks / Trade-offs

- [风险] `sendAlarms` 返回值从"永远 true"变成"如实反映当次发布结果"，是一次可观察的行为变更，跨进程调用方（AIDL `IBackService`）如果对返回值有隐藏的处理逻辑（哪怕现在看起来没用到），行为可能改变 → 缓解：tasks.md 里安排一个专门的验证任务，在改动前找到并读一遍这个 AIDL 接口的所有调用方代码，确认它们目前如何处理返回值，而不是假设"反正现在都是true，改了也没事"。
- [风险] 本地补投队列在设备长期离线时会无限堆积（和 `device-write-back-sync` §5.3 云端队列的问题对称，但方向相反：这次是设备本地队列） → 缓解：给队列加一个类似的失效期（建议与云端队列的30天口径保持一致，但具体数字仍是产品侧判断）。
- [风险] token 存内存，设备重启后所有已登录客户端需要重新登录 → 缓解：这是本设计的有意选择（决策1），如果后续发现运维上不可接受（比如设备频繁被远程重启导致客户端体验很差），再考虑持久化 token，不在本变更里过度设计。

## Migration Plan

1. MQTT 凭据外置（最独立，不依赖其他两块，可最先做，且是最快能验证的——凭据错了连不上 broker 会立刻暴露）。
2. LAN 鉴权（`/login` 签发 token + 中间件校验），完成后 `device-write-back-sync` 的写接口任务组才能真正启用鉴权而不是"暂时零鉴权"。
3. `sendAlarms`/`sendUnloadOils` 行为修正（依赖前置的 AIDL 调用方验证任务）。
4. 回滚策略：三块互相独立，出问题可以单独回滚其中一块而不影响另外两块。
