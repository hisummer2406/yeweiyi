## Context

见 proposal.md - Why，以及 `docs/小程序与PC端集成设计.md` §5（写回同步整体设计，本变更是其中"设备侧接收端"部分的实现）。本设计只覆盖设备侧，不覆盖云端队列/调度（那是新建云端服务的职责）。

## Goals / Non-Goals

**Goals:**
- 设备能接收并应用来自 LAN（PC）和 MQTT（云端/小程序）的配置更新与记录修正请求。
- 每次应用后能明确告知调用方成功/失败（LAN 是同步 HTTP 状态码，MQTT 是异步确认消息）。
- 命令重复投递时不会产生副作用（幂等）。

**Non-Goals:**
- 不实现云端的待同步队列、离线补推调度——那是云端后端的职责，本变更只负责设备端"收到命令后怎么处理"。
- 不解决 PC 与小程序同时修改同一条数据的冲突——按 `docs/小程序与PC端集成设计.md` §5.1 已经定的简化模型（后到写入覆盖先到写入），设备侧只需要"谁最后调用就应用谁的"，不需要在设备侧做额外的冲突检测。
- 不在本变更里实现 LAN 接口鉴权——鉴权是独立的待决策项（见 proposal.md Impact），本变更的写接口先按"和现有只读接口相同的鉴权水平"实现，等鉴权方案定了再统一补。

## Decisions

**1. 按 id 更新复用现有实体类，不新建 DTO。**
`OilInOut`/`CommitWork` 修正请求直接复用 `db/OilInOut.java`/`db/CommitWork.java` 的字段结构（只允许覆盖非主键字段），LAN 请求体与 MQTT payload 用同一套字段命名，保持 PC 和小程序两条路径的契约一致，不产生"两套修正数据结构"的维护负担。
*备选方案*：为修正操作单独设计一套只含"可编辑字段"的精简 DTO。放弃原因：现阶段字段量不大，单独维护一套 DTO 的收益不明显，等真的出现"修正接口暴露了不该暴露的字段"这类问题再拆分。

**2. 命令幂等靠"覆盖式语义"而非去重表。**
配置更新和记录修正都是"把字段设为某个值"（不是"在原值基础上增减"），重复应用同一条命令，结果和只应用一次完全相同。因此设备侧不需要维护一张"已处理命令id"的去重表——命令id只用于云端队列匹配确认应答，设备侧只是原样把它带回去，不用于判断是否已处理过。
*备选方案*：设备侧维护最近N条已处理命令id，收到重复id直接跳过不再应用。放弃原因：既然操作本身幂等，跳过和重新应用的最终效果一样，维护一张去重表反而多一处状态要管理、多一处可能出错的地方。

**3. 确认应答复用现有 `getPropert()` topic 命名模式，新增一个 identifier 而不是新建 topic 结构。**
现有查询类应答都发布在 `thing/event/property/post/{id}`，本变更新增的确认应答复用同一模式，比如 `thing/event/property/post/ackTankSet`，payload 里带 `{commandId, status, appliedValue}`。不引入新的 topic 层级结构，保持和现有 9 个已订阅主题的命名风格一致，降低云端订阅逻辑的额外分支。

## Risks / Trade-offs

- [风险] LAN 写接口先于鉴权方案上线，短期内任何能连上设备局域网的人都能改配置/改历史记录 → 缓解：proposal.md 已明确建议鉴权方案先于本变更实现落地；如果业务上必须先上线写接口，至少要求调用方在请求头带一个共享密钥做最基本的防护，而不是完全裸奔（这个临时方案需要产品侧确认是否接受）。
- [风险] MQTT 弱网环境下命令乱序到达（云端理论上按顺序发送，但 MQTT QoS 和网络抖动不保证严格顺序）→ 缓解：由于命令是覆盖式语义（决策2），乱序到达的最终结果只是"最后处理的那条生效"，和云端队列本身顺序下发的目的一致，不会产生更差的结果，只是云端需要用应答里的 `appliedValue` 而不是自己缓存的"预期值"来更新云端副本。
- [风险] 按 id 修正历史记录时，若传入的 id 在设备本地不存在（比如设备数据被清过，或云端 id 映射出错）→ 缓解：设备侧返回明确的"记录不存在"失败状态，不能静默忽略或误创建一条新记录顶替。

## Migration Plan

1. 先做 MQTT 侧的死主题处理分支（`requestTankTable`/`requestTankSet`/`requestProbeSet`）——风险最低，因为现状是"完全不处理"，新增处理逻辑不会破坏任何现有行为。
2. 再做按 id 修正的持久化层方法（配合 `layer-data-and-hardware-boundaries` 的进度决定加在 Repository 还是 `DBDataManager`）。
3. 再做 LAN 写接口——依赖第2步的持久化层方法。
4. 最后做确认应答——依赖第1、2步都完成，且需要真实的 MQTT 环境验证（本机开发环境无法验证真实的云端往返）。
5. 回滚策略：每一步是独立的新增能力（不修改现有读路径），出问题可以单独禁用某个 handler/topic 处理分支而不影响其他部分。
