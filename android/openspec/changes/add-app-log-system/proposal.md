## Why

测试同事反馈：接多根**旧**中成探针时，偶尔出现持续几分钟、多个罐轮流触发的高温报警；新探针没有反馈过这个问题，也不是插拔探头时触发的。之前读代码排查过，没有找到原因。现场能复现，开发机上不能，所以需要靠日志采集现场数据。

现有的日志设施不够用：

| 现有设施 | 不足之处 |
|---|---|
| `log/LogCatHelper` | 用 `Runtime.exec("logcat *:w \| grep ...")` 执行，不经过 shell，管道符大概率不生效（推断，未经真机确认）；不切分文件、不封顶、不清理 |
| `manager/ProbeTrafficRecorder` | 是编译期开关，要打专门的包；一直全量写、不封顶；用途是采集单测 fixture |
| `crashAppLog` | 只记崩溃 |
| 报警记录表 | 只有"时间、罐号、值"，没有原始报文 |

以后其他功能也需要日志，所以这次直接建一套统一的日志体系，旧探针高温误报排查作为它的第一个使用方。

## What Changes

- 新建统一日志体系：按模块（`PROBE`/`ALARM`/`CLOUD`/`STOCK`/`SYSTEM`）分文件，存放在 app 私有目录 `filesDir/logs`；文件按大小切分，按模块封顶，**全部日志总计不超过 200MB**；超过保留期自动删除，剩余空间不足时暂停写入
- **按级别过滤**（E/W/I/D）：
  - 默认就开启、记 W（正常工况一天不到 1MB，现场第一次出问题就有记录）；关闭开关后只记 E
  - 用户打开开关后，可以选择记录到哪一级，默认 W
  - 选 D（详细模式）时 24 小时后自动退回 W
  - 级别设置持久保存，重启后不变
- **业务事件一律走级别策略**，重要的（包括报警产生/恢复）记 E，默认就会记录；只有崩溃和日志体系自身的事件（启动会话头、级别变更、导出、清空）不受级别限制
- 级别控制做成统一接口，预留按模块、带时长的设置方式，以后由**云端针对指定设备下发**；这次不接云端（协议字段要先和云端对齐）
- 统一行格式 `时间 [模块] 内容`，由日志体系封装，调用方只传模块、级别、事件名和键值对
- 写入走后台线程，不阻塞串口轮询；ERROR 和系统事件立即落盘，防止现场断电丢失；统一脱敏，凭据不写入日志
- 高级设置页底栏加「导出日志」按钮（点击直接导出）；长按进入「日志诊断」页（日志记录开关、级别选择、当前级别和来源、详细模式剩余时长、占用空间、清空），给技术支持用。内容区原有布局不动
- 导出：打成一个 zip，放到外部存储根目录（`/sdcard/`），除各模块原始文件外，另附按时间合并好的 `all.log` 和 `device-info.txt`（版本、设备编号、当前级别、各罐配置快照）；**这次不直接导到 U 盘**
- 崩溃信息同时写入 `SYSTEM` 模块；`LogCatHelper` 先在真机上确认实际产物，再决定是否停用
- 第一个使用方：在中成协议 45 帧（温度应答）和高温报警处按级别埋点（W：温度异常和报警前报文；I：通讯摘要；D：逐帧明细）。**只加日志，不改解析和报警判定**
- 新增类一律用 Kotlin：项目接入 Kotlin 插件 1.7.22（这是 Gradle 6.7.1 能用的最高版本线），已有 Java 代码不改写

**不在本次范围**：
- 修复高温误报本身（要等现场日志确认根因后单独立项）
- 云端下发日志级别、远程拉取日志（只预留接口）
- 导出到 U 盘
- 修改 `ProbeTrafficRecorder`
- 给 `CLOUD`/`STOCK` 补具体埋点

## Capabilities

### New Capabilities

- `reliability/app-logging`：应用日志的存储、级别过滤、容量、脱敏和导出契约
- `reliability/probe-temperature-diagnostics`：中成协议温度应答与高温报警的可追溯性契约，即现场日志必须足以判定误报来源

### Modified Capabilities

无。

## Impact

- **新增代码（Kotlin）**：`logic/applog/`（纯逻辑核心，JVM 单测覆盖）、`applog/AppLog`（门面）、`applog/ProbeLog`/`AlarmLog`（领域日志，以后每个业务领域一个 `XxxLog`）、`fragment/LogSetFragment` 和对应布局
- **构建**：根 `build.gradle` 加 `kotlin-gradle-plugin:1.7.22`，`app/build.gradle` 加 `kotlin-android`；APK 会多出 Kotlin 标准库（项目已开启 multidex）
- **改动的已有 Java 代码（只加日志调用）**：`application/MyApplication`（初始化）、`crashAppLog/CrashAppLog`（崩溃落盘）、`manager/SerialPortManager`（收帧）、`factory/ZhongChengCompany`（45 帧）、`manager/AlarmDetection`（高温产生/恢复）、`manager/AlarmManager`（所有报警产生）、`fragment/SetSeniorFragment`（入口）
- **触及硬件/协议层，必须真机验证**：`SerialPortManager`/`ZhongChengCompany` 只加日志调用，但它们跑在串口轮询线程上。本机只能验证编译和单测，**无法验证对轮询时序有没有影响、现场能不能抓到数据**
- **新增文案**：精简为 11 条（级别名直接显示 E/W/I/D，不进资源），中、英、西三套；英文和西班牙文按用户要求由 AI 翻译，待 review
- **存储**（都是推断，需要真机核对）：W 级正常不到 1MB/天（一次 5 分钟、4 个罐的误报约 0.2MB）；I 级再多约 0.2–0.4MB/天；D 级约 50–60MB/天，24 小时自动到期前写出的量（约 60MB）能被 PROBE 80MB 上限完整保留
- **对三条硬约束**：遵守约束 1（纯新增，解析和报警逻辑不变；Kotlin 只用于新增类，不重写旧代码）；遵守约束 2（纯逻辑核心先写单测；串口线程上的埋点无法用单测覆盖，靠真机验证）；遵守约束 3（服务于协议层问题的现场取证）
