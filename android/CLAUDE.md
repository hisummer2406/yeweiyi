# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**安卓液位仪 (Android Liquid Level Meter)** — a native Android app, package `com.sansen.yeweiyi`, that runs on a dedicated landscape-orientation hardware terminal for monitoring oil storage tanks (油罐). It talks to physical liquid-level probes over RS-232/485 serial and/or TCP socket, decodes vendor-specific binary protocols, persists readings locally, and exposes an embedded HTTP server so other devices on the LAN (e.g. a PC) can query the data.

This was previously scaffolded from the `goldze/MVVMHabit` template (Java, MVVM + DataBinding + RxJava2), but as of the current code that template has been **entirely superseded** — the `mvvmhabit` module is gone, DataBinding/RxJava-first architecture is gone, and this is now a self-contained, older-style Android app (compileSdk 27, minSdk 21) built around singleton managers rather than MVVM.

### Modules (`settings.gradle`)

- `app/` — the application, package `com.sansen.yeweiyi`. All real business logic lives here.
- `xutilslibrary/` — a vendored copy of the old **xUtils** framework (`com.lidroid.xutils`: ORM `DbUtils`, `HttpUtils`, view-injection). Used as the local persistence/HTTP layer instead of GreenDAO or Retrofit-first code.

### Orphaned directories — do not edit

The stray root-level `java/` and `src/` duplicate source trees were removed (commit `8f8373c`). If they reappear, they are not referenced by `settings.gradle` or any build.gradle — always edit the real module paths under `app/src/main/java/...` and `xutilslibrary/src/main/java/...`.

Within `app/src/main/java` itself there are also several non-namespaced top-level packages that predate the `com.sansen.yeweiyi` package (`asynmsg`, `bean`, `recycle`, `storage`, `rxjava`, `log`, `base`, `serialport`, `atg`, `com.example.x6.gpioctl`). These *are* compiled and in use (e.g. `log.LogCatHelper`, `serialport.manager.SerialPortManager` are referenced from `MyApplication`), but note there are two different, unrelated `BaseFragment` classes — `base.BaseFragment`/`base.BaseVM` (root package, appears to be dead/unused leftover) vs. `com.sansen.yeweiyi.base.BaseFragment` (the one actually extended by real screens). Check imports carefully before assuming which one a file uses.

- Commits `6ae4e3f` through `ada562e` (阶段 0 and 阶段 1) were written *before* the toolchain existed and were merged unverified. Later commits are compile-verified.
- `testDebugUnitTest` reports `UP-TO-DATE` and prints nothing when inputs haven't changed — a stale pass looks identical to a fresh one. Run `./gradlew :app:cleanTestDebugUnitTest :app:testDebugUnitTest`, or read `app/build/test-results/testDebugUnitTest/*.xml`, before claiming tests passed.

A green build here proves compilation only. **Nothing about serial/probe hardware behavior can be verified on this machine** — protocol changes still need a real device.

### Line endings are LF, pinned by `.gitattributes`

The repo was CRLF (Windows origin) until 2026-08-07, when commit `5c6e6a3` normalized all 410 text files to LF and added `.gitattributes` (`* text=auto eol=lf`; `*.bat` stays CRLF; binaries explicitly marked). Don't reintroduce CRLF, and don't let a bulk-edit script rewrite whole files — that is what produced the mixed state in the first place (a one-line `catch` fix in `MD5utils.java` showed up as `32+/31-`).

`git blame` on any file older than that commit needs `-w`, or one-time `git config blame.ignoreRevsFile .git-blame-ignore-revs`.

### Secrets are injected at build time — not hardcoded

`app/build.gradle` reads `local.properties` and injects credential values into `BuildConfig` — `PRODUCT_KEY`, `PRODUCT_SECRET` (still used by the legacy Aliyun-style REST device registration in `AlarmDetection`/`IDevice`, unrelated to MQTT), `REQUEST_ENCRYPT_KEY`, `BASE_URL`, `PROVISION_DEVICE_KEY`/`PROVISION_DEVICE_SECRET` (ThingsBoard Device Profile provisioning key pair, shared by every device of the model — see next paragraph); `ApiConfig` just re-exports them. `local.properties` is untracked — copy `local.properties.template` and fill it in. Missing keys log a `[配置缺失]` warning at build time and compile to empty strings.

`MQTT_USERNAME`/`MQTT_PASSWORD` (added 2026-08-14) were removed 2026-09-01 as part of the ThingsBoard migration (see "ThingsBoard CE device protocol" below) — that shared, build-time-injected account is exactly what "每台设备独立凭据" replaces. Per-device ThingsBoard access tokens are obtained at runtime instead, stored via `manager/ThingsBoardCredentialStore` (`SharePrefUtil.TB_DEVICE_ID`/`TB_ACCESS_TOKEN`), not through this build-time channel. `fragment/ThingsBoardSetFragment` (高级设置 → 云平台设置) is the entry point: the installer types broker host/port + the device number printed on the sticker (the device can't read it itself and has no scanner); with the token field left empty, `ThingsBoardManager.provisionAccessToken()` claims a token via ThingsBoard's own Device Provisioning MQTT API (`provision` username, `/provision/request`) using the build-time key pair, with hand-typed token as fallback. As of 2026-10-07 the success path is verified on a real device (rk3562_t, Android 13) against the real broker `8.154.38.176:8883` over TLS — the broker uses a private CA (`yeweiyi-internal-ca`), shipped as `app/src/main/assets/thingsboard_ca.pem`; failure paths (re-provision, unregistered number) are not yet device-tested; flow, failure handling and the cloud-side setup it depends on are in `docs/设备配网流程-编号与Provisioning.md`. `accessToken` is encrypted with an Android Keystore AES/GCM key before it touches disk (falls back to plaintext + a logged warning only below API 23, which is not a real deployment target for this hardware); `deviceId` stays plaintext since it's just the MQTT client ID, not secret material.

There are two non-secret **flags** on the same channel, injected via `flagField` instead of `secretField` (missing = `false`, no warning): `PROBE_RECORDING` (`sansen.probeRecording`) turns on `manager/ProbeTrafficRecorder`, which writes probe traffic to `/sdcard/yeweiyi-probe-record/` for golden-master capture — keep it off in any build that ships; `THINGSBOARD_USE_TLS` (`sansen.thingsboardUseTls`) selects `ssl://` vs `tcp://` for the ThingsBoard MQTT connection — enable for any real deployment, leave off for local/dev broker testing.

Credentials hardcoded before commit `6ae4e3f` are in git history and must be treated as leaked.

Key `app/build.gradle` facts:
- `compileSdkVersion 27`, `minSdkVersion 21`, `targetSdkVersion 27`, landscape-only (see manifest).
- `multiDexEnabled true`, native build via `externalNativeBuild { cmake { path "src/main/cpp/CMakeLists.txt" } }`.
- versioning is vendor-specific (`versionName "NEW.SS.A.Y1.00"`), and the APK output filename is auto-suffixed with version + date + build type.
- The root `build.gradle` still declares a `greendao-gradle-plugin` classpath dependency, but no module applies the `org.greenrobot.greendao` plugin or uses GreenDAO anymore — it's vestigial from the old template and can be ignored (or removed if cleaning up).
- Dependencies are a large pile of local jars in `app/libs/` (Baidu Maps/TTS/Push SDKs, Apache POI 3.10 for Excel export, Tencent TBS X5 webview kernel, MQTT client, AndServer, Apache httpclient/mina, `sun.misc.BASE64Decoder`, an internal `xzjh_interface_*.jar`). Treat these as fixed/vendored artifacts — most have no current Maven-hosted release, so don't try to "upgrade" them without checking hardware/vendor SDK compatibility first.

There is no real unit/instrumented test suite.

## Architecture

### App entry & global setup

`com.sansen.yeweiyi.application.MyApplication` (declared in `AndroidManifest.xml`) initializes, in `onCreate()`: crash handling (`CrashApphandler`), file logging (`log.LogCatHelper`), `CRCheck`, the serial port manager (`serialport.manager.SerialPortManager`), the local DB (`DaoHelp`, an xUtils `DbUtils` wrapper), sound alerts (`SoundManager`), and several data managers (`DBDataManager`, `OilcanDataManager`, `SaveOilManager`). It also loads the persisted `LevelmeterInfo` device config and sets up locale/language switching. `MainActivity` (`com.sansen.yeweiyi.activity.MainActivity`) is the sole real Activity and hosts everything else as Fragments (see manifest — landscape-locked).

### Data flow: hardware → app → UI / LAN

- `manager/` — singleton managers: `SerialPortManager` (JNI serial comms with the probe hardware), `SocketManager`/`TCPClient` (network comms with the probe or other devices), `AlarmManager`/`AlarmDetection`/`SoundLightManager` (alarm state + audible/visual alerts), `OilcanDataManager`/`SaveOilManager` (business data, now read/write through `repository/` for their domain data — see below), `DBDataManager` (persistence access for everything *not* yet moved to `repository/` — see below), `MyTimeTask` (polling/scheduling), `InOilManager` (出/入库 event detection glue — see below), `ThingsBoardManager` (ThingsBoard CE MQTT glue — see "ThingsBoard CE device protocol" below).
- `repository/` — the persistence entry point for four domains, each an interface + `XxxRepositoryImpl` singleton (`getInstance()`) calling `DaoHelp`/`DbUtils` directly: `OilTankRepository` (`OilCanSet`/`OilCanTable`/`ProbeToOil`/`Sideleakage`/`OilCanMapper`/`OilExploration`), `StockRepository` (`OilInOut`/`OutStock`/`StockSave`/`DetailInoutRecord`), `AlarmRepository` (`Alarm`), `ShiftRepository` (`CommitWork`). New code touching these six entities should go through the matching Repository, not `DBDataManager`. See `openspec/changes/archive/2026-11-02-layer-data-and-hardware-boundaries` for how these were split out of `DBDataManager` (strangler-fig: old methods marked `@Deprecated`, not deleted) and for the one method-per-domain quirks that were deliberately preserved rather than fixed during the migration.
- `logic/inout/` — pure Java (no `Context`/Android singletons) state machine that decides whether a run of liquid-level readings constitutes a stock-in/stock-out event: `TankLevelTracker` (per-tank state machine — dead-band debounce, then requires both a time and a height threshold before firing, keeps waiting instead of discarding when only one threshold is met), `MultiTankInOutDetector` (per-tank tracker registry, replaces a former 16-slot fixed array), `InOutEvent`/`InOutDirection`/`InOutThresholds` (value types). `manager/InOilManager` is the glue layer: assembles `InOutThresholds` from `Singleton`, feeds readings in, and on a produced `InOutEvent` fills in live `OilcanDataManager` fields and persists to `OilInOut`/`OutStock` — direction is decided once inside `TankLevelTracker` and never re-derived downstream. Covered by JVM unit tests (`logic/inout/*Test.java`) since it has no Android dependency. See `openspec/changes/rewrite-stock-inout-detection` for the rationale (the previous implementation zeroed out its tracked state on the first threshold check that didn't pass, instead of continuing to wait — the main cause of missing 出库/入库 records).
- `factory/` — per-vendor protocol parsers for different probe hardware brands (`LDCompany`, `LD2Company`, `VR350Factory`, `ZhongChengCompany`), all implementing shared interfaces (`ICreateTable`, `IParseDataListener`). This is the extension point for adding support for a new probe vendor/protocol.
- `structbean/` — byte-level struct definitions (`*In.java`) for the serial/socket protocol frames exchanged with probe hardware.
- `db/` — plain POJO entities (`OilCanSet`, `OilInOut`, `Alarm`, `User`, `Authorization`, etc.) persisted via xUtils `DbUtils` (see `db/help/DaoHelp.java`), not GreenDAO. Six of these entities (see `repository/` above) are read/written through a domain Repository; the rest still go through `DBDataManager` directly.
- `fragment/` — the actual UI screens hosted inside `MainActivity` (`MainFragment`, `OilCanFragment`, `InOilFragment`, `OutStockFragment`, `AlarmFragment`, `SetFragment` + sub-settings fragments, `BaoBiaoFragment` for reports, etc.).
- `web/handler/` — request handlers for an embedded AndServer HTTP server (`LoginHandler`, `AlarmHandler`, `OilDischarge`, `UploadHandler`, `FileHandler`, `ServerManager`) so external clients on the LAN can pull data from the device.
- `okGoUntils/` — an OkGo-based networking helper, used alongside (not instead of) xUtils `HttpUtils` — check which a given class actually uses before assuming.

### ThingsBoard CE device protocol (`logic/thingsboard/`, `manager/ThingsBoard*`)

As of 2026-09-01 (`feature/thingsboard-device-protocol`, tracked upstream as issue #37/#36/#35), `BackService` talks to ThingsBoard CE's native device MQTT API instead of the old Aliyun-style Alink topics (`sys/{productKey}/{deviceName}/thing/...`, formerly built by the now-deleted `service/MqttUtil`). No dual-protocol switch was kept — this is a full cutover, not an additive path.

- `logic/thingsboard/` — pure Java (no `Context`/Android singletons), mirrors the `logic/inout/` pattern: `ThingsBoardTopics` (fixed `v1/devices/me/...` topic builders), `ProtocolVersion` (an `int`, matching the cloud's `protocol.Version`), `DeviceCredentials`/`DeviceCredentialStore` (per-device access token, not a shared build-time account), `ReconnectBackoff` (exponential, replaces the old fixed 60s reconnect check), `TelemetrySnapshotBuilder`/`AlarmEventBuilder` (payload shape — see fixtures under `app/src/test/resources/thingsboard/`), `TelemetryScheduler` (single-flight 30s snapshot scheduler), `PendingAlarmStore` (bounded offline backlog for alarm/recovery/cmdResult events only — normal snapshots are dropped, not queued, while disconnected), `BrokerTls` (broker-URI host parsing, private-CA trust chain, and hostname verification — see "TLS" below). `logic/thingsboard/rpc/` is the generic server-side RPC framework: `RpcRequestEnvelope` (parses `{method, params:{commandId, expiresAtMs, issuedAtMs, protocolVersion, operator, reason, args}}` — field names/types match the cloud's `protocol.Envelope`, not the device's own historical guesses), `ProcessedCommandStore` (commandId-keyed idempotency + restart recovery — any non-terminal record left over from a killed process is resolved to `FAILED`, never replayed as "maybe succeeded"; `Persistence.saveAll` returns whether the write actually reached disk, and `record()` propagates that), `RpcDispatcher` (parse → protocol/expiry check → dedup → `RECEIVED` ack → execute → async `cmdResult`; **if the `RECEIVED` record can't be persisted the handler is not executed at all** — that record is the only thing preventing a re-execution after a power loss, so the command is rejected outright instead), `RpcMethodRegistry`/`RpcMethodHandler`. `RpcAckPublisher` and `RpcResultPublisher` are two separate channels, not one — see the next bullet. Covered by JVM unit tests (`logic/thingsboard/**/*Test.java`).
- **ACK and command result are two different channels, on purpose.** The RPC response topic (`v1/devices/me/rpc/response/{id}`) only ever carries `received`/`rejected` (`RpcAckPublisher`) — every "already decided before running the handler" outcome (bad protocol version, expired, unknown method, dedup-record write failure) is reported there as `rejected`, with the real reason in `errorCode` (the internal `ProcessedCommandStore` record still keeps the true status — `EXPIRED`/`FAILED` — for dedup bookkeeping; only the wire-facing ACK status is collapsed to `rejected`). The command's actual outcome (`executing`/`succeeded`/`failed`) is reported asynchronously as a `cmdResult` telemetry event (`RpcResultPublisher`, reusing `PendingAlarmStore`'s offline backlog) — never as a second publish on the ACK topic. The one exception: replaying a cached terminal result for a duplicate `commandId` goes out immediately via the ACK channel with `duplicate=true`, since the answer is already known and doesn't need a new async round-trip. This split matches the cloud's `internal/protocol.Ack`/`CmdResult` contract (issue #39) — the original single-channel design (both ACK'd on the same topic) is what made the cloud's own `internal/protocol.Ack.Status` doc comment a lie.
- `manager/ThingsBoardManager` — the glue layer (role like `InOilManager` for `logic/inout`): owns `ThingsBoardMqttConnection` (Paho, TLS via `ApiConfig.THINGSBOARD_USE_TLS`), `ThingsBoardCredentialStore` (SharedPreferences-backed `DeviceCredentialStore`, `accessToken` Keystore-encrypted — see the secrets section above), a `snapshotSeq` counter (monotonic since process start, carried in every telemetry snapshot), file-backed persistence for the RPC dedup table, alarm backlog and active-alarm set (`ProcessedCommandFilePersistence`/`PendingAlarmFilePersistence`/`ActiveAlarmFilePersistence`, all on top of `AtomicJsonFile`: write temp → `fsync` → rename for power-loss safety, and a file that fails to parse is renamed to `.corrupt-<ts>` instead of being silently overwritten — code review M4). `BackService` only calls this class — it doesn't touch `logic/thingsboard` types or Paho directly. `applyUpdatedConnectionSettings(host, port)` is what `ThingsBoardSetFragment`'s save button calls: updates `ThingsBoardMqttConnection`'s (now mutable) broker URI and forces a disconnect/reconnect so a saved change takes effect immediately rather than waiting for the next unrelated reconnect. All of that runs on the `tb-reconnect` thread, never the caller's: `disconnect()` shares a lock with `connect()` (10 s timeout), so doing it on the UI thread could ANR exactly when an installer is fixing a broker that won't connect (code review H8; `stop()`'s disconnect is offloaded for the same reason). Every connect attempt goes through one queue (`scheduleConnectAttempt`/`reconnectNow`) holding at most one pending attempt, tagged with a generation number so a superseded attempt becomes a no-op instead of spawning a second retry chain (code review M2) — before this existed, the broker address came from `SharePreManager.getIpBean()`, whose only write path (`saveIpBean()`) also had zero callers and silently fell back to a hardcoded legacy IP (`39.98.62.79:1883`, left over from the pre-ThingsBoard MQTT broker). As of 2026-10-07 that unsaved-default is the ThingsBoard broker `8.154.38.176:8883` instead; devices that already saved an address via the settings page keep their saved value.
- **TLS (`BrokerTls` + `manager/ThingsBoardCaStore` + `manager/SniSocketFactory`)** — `libs/mqtt-client-0.4.0.jar` is Paho from 2013: its `TCPNetworkModule.start()` calls the **no-arg** `SocketFactory.createSocket()` and only then `socket.connect(addr)`, so the socket never learns the target hostname. Consequence: the platform does no automatic SNI **and no hostname verification at all** — both have to be supplied here. Hostname verification lives inside the `X509TrustManager` (`BrokerTls`), not in a post-handshake callback, so it runs before the CONNECT packet — which carries the access token — can reach an impostor. `ThingsBoardCaStore` looks for a private CA at `<filesDir>/thingsboard_ca.pem` first, then `assets/thingsboard_ca.pem`; found → that CA is the *only* trust anchor (matching the cloud's `internal/devicesim`), not found → system trust store. Never read the CA from external storage (any app can write there) and **never add a skip-verification switch** — this connection carries pump/valve commands. `SniSocketFactory` adds SNI (skipped for IP literals per RFC 6066, and unavailable below API 24 — harmless, ThingsBoard is a single-certificate deployment) and pins TLS 1.2+. Covered by `BrokerTlsTest`, which does a real handshake against a local `SSLServerSocket` using fixtures from `tools/generate-tls-test-fixtures.sh`.
- Reference RPC handler: `config.setAlarmThresholds` (`rpc/handler/SetAlarmThresholdHandler`, method name matches the cloud's `MethodConfigAlarmThreshold`) — the "low-risk config change" example the framework was built to prove out, writes through `OilTankRepository`. As of 2026-10-08 two more config handlers follow the same pattern with stricter validation: `config.setTankSettings` (`SetTankSettingsHandler`) and `config.setDeviceSettings` (`SetDeviceSettingsHandler`) — field names identical to the client-attribute keys, whitelist + range check, all-or-nothing; field list and the deliberately-closed fields (low-temp alarm, tank height, probe address, tank shape, sensor length) are in `docs/远程配置下发-字段清单.md`; names/ranges are not yet agreed with the cloud. `HighRiskActionHandler` registers `pump.start`/`pump.stop`/`valve.open`/`valve.close` plus `alarm.mute`/`alarm.clear`/`device.reboot` (all seven method names now match the cloud's `internal/protocol/rpc.go` `Method*` constants exactly, pinned by `HighRiskActionHandlerTest.methodNamesMatchCloudProtocol` — **the pump/valve four were still the pre-migration names (`startPump` etc.) until 2026-09-19**; nothing caught the drift earlier because all seven are unconditionally rejected, so a wrong method name and a right one both currently produce the same externally-visible behavior) and **always rejects** with `FEATURE_DISABLED` — none of these seven are wired to real hardware/business logic. Pump/valve stay closed until issue #34 (interlocks + real-hardware verification) lands; `alarm.mute`/`alarm.clear` need the same real-hardware verification before touching `AlarmDetection`/`SoundLightManager`'s existing state machine (see next bullet) — there is no config flag that opens any of them yet. Note the cloud's `cmd/smoke` install-acceptance script (issue #40) **never talks to an Android device**: it provisions its own throwaway ThingsBoard device and drives it with the cloud's built-in simulator (`internal/devicesim`, created unconditionally in `cmd/smoke/main.go`; there is no flag to point it at a real device). So smoke passing or failing says nothing about this app — acceptance of the Android side (including `alarm.mute`) has to be done by hand on a real device.
- **Alarm raise/recover reporting mirrors the local alarm logic exactly (2026-10-04, V1-T1).** `manager/CloudAlarmReporter` is called from `AlarmManager.addAlarmState` (raise — every local alarm, including `SerialPortManager`'s probe-disconnect, passes through there) and from `AlarmDetection`'s "condition no longer holds" `else` branches plus `SerialPortManager`'s comms-recovered branch (recover). It does **no threshold logic of its own** — the user explicitly asked that cloud ACTIVE/CLEARED follow the existing local behavior, so local quirks (e.g. an alarm condition already present at boot never fires, because the `Singleton` flags start un-armed) show up in the cloud unchanged; they're logged as deferred defects in `docs/ThingsBoard两版迭代执行方案.md` §3.10, don't "fix" them as part of reporting work. `logic/thingsboard/ActiveAlarmTracker` (pure Java) dedups raises, only emits CLEARED for something previously ACTIVE, mints a per-occurrence `alarmId` (`TYPE-tank-raisedAtMs`, protocol §4.1), persists the ACTIVE set to `filesDir/thingsboard_active_alarms.json` so a CLEARED can still be sent after a restart, and rolls up `tank{N}.alarmState` (probe-disconnect → `FAULT`, any other → `ALARM`, else `NORMAL`) for the snapshot. The old `AlarmCoordinator` → `SocketManager.sendAlarm` → `BackService` path is retired. Demo mode (`TEST_DATA`) reports nothing, as before. Ordering/loss invariants that a 2026-10-05 review found broken and that must not regress: (a) every instant event (alarm/stockEvent/cmdResult) goes through `ThingsBoardManager.publishEventInOrder`, which queues behind any backlog instead of publishing live past it — otherwise a CLEARED can overtake its own queued ACTIVE; (b) `CloudAlarmReporter` decides the transition and submits it under one lock, because raises and recoveries arrive on different threads; (c) the backlog eviction policy (`AlarmEventBuilder.EVICTION_POLICY`) only ever drops an ACTIVE, together with its same-`alarmId` CLEARED; a CLEARED is "protected" and is skipped by the fallback eviction too — it is dropped alone only when the whole queue is CLEARED events (code review M3); (d) `CloudAlarmReporter.onTanksReloaded` (at start and after each `OilcanDataManager.refresh()`) clears ACTIVE alarms of tanks no longer enabled, since those are never polled again. Any of these failing leaves a cloud alarm stuck ACTIVE forever.
- **Also not migrated in this cutover**: the old Alink "pull historical records over MQTT" services (卸油/报警/交班/侧漏/罐表/罐设置/探头设置 `request*` topics) were deleted along with the Alink topic scheme and were **not** reimplemented as RPC methods — that's a bounded, deliberate scope cut (issue #35 only asked for one reference low-risk handler), not a silent regression. Re-adding them follows the exact same `RpcMethodHandler` pattern as `SetAlarmThresholdHandler`. Client attributes (one combined message, sent on every successful (re)connect **and** after every `OilcanDataManager.refresh()` via its `setConfigChangedListener`): `ClientAttributesBuilder` publishes the §5.1 keys that have a real data source — `protocolVersion`, `tankCount` (max tank id, same as the snapshot), `tank{N}.probeAddress`/`probeType`/`capacityL`; `TankCalibrationAttributeBuilder` (issue #42 待办1) adds `tank{N}.calibrationHeightMm`/`calibrationVolumeL` (a key the cloud has no consumer for yet; non-finite points are dropped — a NaN once made Gson throw and crash the app). As of 2026-10-08 `TankSettingsAttributeBuilder` (every 罐设置页 field per enabled tank) and `DeviceSettingsAttributeBuilder` (出入库 height/time thresholds) are added too — key names/units were chosen on this side and are **not yet agreed with the cloud**; see `docs/ThingsBoard接入现状与待办.md` §3.5. Settings changes trigger a debounced republish via `OilTankRepository.setOilCanSetChangedListener` and `ThingsBoardManager.requestClientAttributesPublish()`. `probeType` is the serial protocol name, matching the serial settings page wording (`ZHONGCHENG`/`MODBUS`/`4-20MA`), not the cloud fixture's measuring-principle wording — pending cross-repo agreement. Beware: `OilCan.getProbeType()` ignores its own `probeType` field and returns `Singleton.ChuanKou2` — the device-wide "串口 2" protocol choice in `ChuanKouFragment` (0 中盛 / 1 标准 Modbus → `LDCompany` / 2 4-20mA → `LD2Company`), so `setProbeType()` having no callers does **not** mean the value is constant. `deviceModel`/`hardwareVersion`/`localControlMode` are deliberately not sent (no defined value / no such device state).
- **Shared attributes (server→device push) — partially implemented as of 2026-09-19.** `ThingsBoardMqttConnection` now subscribes to `ATTRIBUTES_PUBLISH` (live push) and `ATTRIBUTES_RESPONSE_SUBSCRIBE` (request/response) in addition to the RPC topic, and `ThingsBoardManager.requestSharedAttributes()` fires an `attributes/request` for `reportIntervalSec` on every successful (re)connect — subscribing alone does not replay already-set values, only future changes, so a fresh connection would otherwise never learn the current value. `SharedAttributesParser` (pure Java, JVM-tested) parses both the flat push shape and the `{"shared":{...}}`-wrapped response shape; a valid value calls `TelemetryScheduler.updatePeriod()`, which reschedules without a restart per protocol-v1.md §5.2's "must take effect without a reboot" requirement. **`alarmThresholds` is deliberately not parsed** — the protocol doc gives no field shape for it (unlike `config.setAlarmThresholds`'s RPC `args`, which is defined), and guessing wrong would apply corrupted thresholds silently; this follows the same "don't freeze an undefined shape" precedent as `config.setTank`/`config.setProbe` having no registered handler.
- **Cross-repo protocol status (updated 2026-09-16 — supersedes the 2026-09-04 "two mutually incompatible V1s" note): this repo's telemetry/RPC/alarm shapes now match what `yeweiyi-cloud` already shipped (`main@5ff243b`'s `internal/protocol/*.go`), closing the structural gap from issue #39 on the device side.** Telemetry uses the cloud's flat `tank{N}.{field}` keys (not the old nested `tanks[]` array) plus `tankCount`/`snapshotSeq`; the RPC envelope reads `expiresAtMs`/`issuedAtMs`/integer `protocolVersion`; `config.setAlarmThresholds` replaces the old `setAlarmThreshold`; the ACK/`cmdResult` split matches the cloud's "ACK only ever means received/rejected" contract; the alarm event uses the `alarm` key with `alarmId`/`status: ACTIVE|CLEARED`/`severity`/`tank`/`text`. **What's still a real gap, not overclaimed parity:**
  - Alarm recovery and per-tank `alarmState` are wired (see the bullet above) but **not yet verified on real hardware**.
  - `LOW_TEMPER`, 出入库 (`IN_OIL`/`OUT_OIL`/`*_OILing`), `NET_ERR_CONN`, `RELAY_DISCONNECT`, `OIl_EXPLORATION` have no home in the cloud's closed alarm-type set and are silently not reported over the `alarm` channel — by design (see `AlarmEventBuilder`'s type mapping table), not oversight. 出入库/交班 still have no upstream channel on either side at all — that needs a product decision, not a technical one.
  - `alarm.mute`/`alarm.clear`/`device.reboot` are registered but always `FEATURE_DISABLED` (see above). (The cloud's `cmd/smoke` can't be used to check this — it only drives the cloud's own simulator, see above.)
  - Client attributes cover the §5.1 keys with a real data source but not `deviceModel`/`hardwareVersion`/`localControlMode`, and `probeType` naming is unagreed (see above) — and `alarmThresholds` shared-attribute push is not parsed at all (see above).
  - Severity assignment in `AlarmEventBuilder`'s type mapping table (CRITICAL for double-threshold breaches, MAJOR for everything else mapped) is this pass's own judgment call, not cross-repo-confirmed — re-check with the cloud/product side before treating it as settled.
  - `LEAK_SUSPECTED`/`OVERFILL_RISK` remain in the cloud's protocol with no Android-side source signal — no business logic on this side currently detects either condition.
  **The protocol is still not frozen: don't add new fields to either side's protocol implementation without cross-repo confirmation, now that the two sides' shapes actually match.** See issue #39/#40 for the full history of the reconciliation.

## Testing

`app/src/test/` has real tests as of commit `ada562e` — `CRCheckTest` and `DataUtilsTest` (plus the stock `ExampleUnitTest`). They run on plain JVM; no device or Robolectric needed.

**What is and isn't unit-testable here:** `DataUtils` imports `R`/`MyApplication`/`ATGJNI` but has no static initializer block, so class loading never triggers `System.loadLibrary` — its byte/hex helpers test fine on JVM; only `getLitre()` (ATGJNI) and `getOilType()` (MyApplication) must be avoided. `CRCheck` has no `import` lines, but it is *not* dependency-free: line 1480 calls `DataUtils.shortToByte` from the same package, and same-package references need no import. The `factory/` vendor-protocol classes **cannot** be tested on plain JVM — `LDCompany` and friends import `android.content.Context` and `SparseArray`, so testing them needs Robolectric or an extracted pure-parsing layer.

> Grepping for `^import` does **not** establish that a class is self-contained — same-package references are invisible to it. Verify with the compiler, not with grep.

### ⚠️ `git grep` regex silently fails here — use `-F` for deletion safety checks

This environment's `git grep` is ugrep-backed, and two common constructs **match nothing and exit 0** instead of erroring:

- `\|` alternation — `git grep "R\.string\.foo\|@string/foo"` finds nothing, ever
- `\b` word boundary — `git grep -nE "R\.string\.foo\b"` finds nothing, even though `-E` without `\b` finds it

Both produce a *silent false negative*, which is the worst possible failure mode for "is this safe to delete?" checks. A resource deletion in this repo was made on such a bad check and broke the build (`R.string.apkurl` in `LoginHelper.java:67`).

**Before deleting anything, verify references with `git grep -F` (fixed string), one term per invocation.** Reserve regex for exploration, never for a safety gate. `grep -rlw` (system grep, no alternation) has been reliable for whole-word class-name scans.

Also note resources can only be reached by name via `getIdentifier()` — this project has none, so `R.` / `@string/` references are exhaustive.

## Known landmines

Traps that compile cleanly and fail at runtime — check these before refactoring:

- **`android:onClick` reflection binding — eliminated as of 2026-08-19 (`split-main-activity` §1, PR #22, unmerged as of this writing).** All 34 `res/layout` bindings that used to reference `MainActivity` methods by string name are now `setOnClickListener` calls, compile-time visible. Enumerating them surfaced more than the original plan expected: a dead side-menu (`menu_right` in `activity_main.xml`, always `visibility="gone"`, never toggled from Java, 4 of its 7 bindings pointed at methods that didn't exist at all) was deleted outright; two fully orphaned layouts (`activity_login.xml`, `fragment_recode_storage.xml`, zero references anywhere) were deleted; 6 bindings turned out to already be shadowed by a real `setOnClickListener` set later in the owning Fragment's `findView()` (Android lets the later call win over the XML-declared one), so they were never actually reachable — deleting the dead XML attribute was enough, no new listener needed. Only 18 of the original 34 needed a real conversion. If this file reappears in a landmine-hunting context, treat the pattern (not this specific instance) as the reusable lesson: before assuming a `android:onClick`-bound method is a live crash risk, check whether the same View already has a programmatic listener set elsewhere — it may be inert.
- **Duplicate method pairs.** `DataUtils.HexString2Bytes` / `hexString2Bytes` and `byte2Short` / `byteToShort` are byte-identical duplicates. `CRCheck.crc16` / `crc162` differ *only* in returned byte order (`"4B37"` vs `"374B"`) — picking the wrong one silently produces a bad checksum.
- **Three `bytesToHexString` overloads with different formats.** With `size` → uppercase, space-separated; without → lowercase, no separator; single-byte → lowercase and *not zero-padded* (`0x0A` → `"a"`). `CRCheck.getModBusCRC` is likewise unpadded lowercase.
- **`DataUtils.hexToFloat` throws on any negative float.** It uses `Integer.parseInt(hex, 16)`, which overflows once the IEEE-754 sign bit is set (`-5.0f` = `0xC0A00000`). Currently unreferenced, but this device reads negative temperatures — fix with `Integer.parseUnsignedInt` before using it.
- **`DataUtils.SumCheck` is not a sum.** It XORs all bytes then subtracts `0x80`.
- **Two same-named `SerialPortManager` classes.** `com.sansen.yeweiyi.manager.SerialPortManager` (protocol orchestration: polling, `factory/` vendor dispatch, alarm linkage, UI callback) is not the HAL. `serialport.manager.SerialPortManager` (263 lines, almost no callers) is the real HAL — raw JNI byte send/receive. UI/business code must always go through the `manager/` one; direct calls to the `serialport.manager` one bypass the orchestration layer entirely. As of 2026-08-19 the orchestration one no longer `import`s `BaseActivity` — it calls back through `manager/DataRefreshCallback`, implemented by `BaseActivity` (see `openspec/changes/archive/2026-11-02-layer-data-and-hardware-boundaries` §8); the callback re-posts onto `BaseActivity`'s own `Handler` to preserve the original background-thread → main-thread hop.
- **"A listener is set" ≠ "the callback actually runs" — 2026-09-21, found while auditing Spanish (`values-es`) coverage.** Translating a string is wasted effort if the code path that displays it can't be reached, and this codebase has a lot more unreachable code than the `android:onClick` sweep above found. Checking "is a listener registered" is not enough — the listener's *method body* has to be read. The concrete trigger: `InOutAdapter.onBindViewHolder()` sets a real `setOnClickListener`, but its `onClick(View v)` body is empty (`{}`) — short-tapping a 进出库 list row does nothing; only long-press (a different dialog) fires. That made `dialog_detail_inout.xml` and its inflation site (`InOilFragment.onClick(int)`) fully dead despite looking wired end-to-end. A follow-up audit (2 rounds of parallel agents, then manual re-verification of every "reachable" claim against its actual listener/callback body, then a further round the user prompted by naming specific suspects) found 107 more string keys unreachable across 25 locations this way — empty adapter-listener bodies, `Fragment.onHiddenChanged()` that can never fire because the `Fragment` is always freshly `new`'d instead of cached-and-shown, a `switch` branch (`ActivityDialog` `value==7`) nobody ever passes, a `Service` (`BackService`) declared in the manifest but never `startService()`'d, a `BroadcastReceiver` (`UsbStateReceiver`) only ever registered statically in the manifest for `ACTION_MEDIA_MOUNTED`/`ACTION_MEDIA_EJECT` — broadcasts the platform has refused to deliver to manifest-registered receivers since API 24, well under this app's `targetSdkVersion 27` — a data field (`MainFragment.gasExplor`) that's declared but never assigned so the adapter's `getCount()` is permanently 0, and one that looked like the biggest single class but turned out to be a cautionary tale about stopping the consumer-side check too early: `OilMessage.getState()` (called correctly, `setType()` sites genuinely reachable) was first found to have two dead consumers (`AlarmCoordinator`'s target `TextView` sits inside a `visibility="gone"` container that's never flipped visible — same container `activity_main.xml`'s `onLoading` already implicated — and its fallback path forwards into the dead `BackService`) and got marked fully unreachable on that basis — but there was a *third* consumer, `AlarmRepositoryImpl.saveAlarm()`, which stores `oilMessage.toString()` into the `Alarm.info` column that `AlarmAdapter` displays on the alarm-records screen, and it's very much alive (2026-09-23, the user caught this by just asking why the spreadsheet listed those keys as "used" — checking two consumers and stopping is exactly the same mistake as checking zero). Net effect after the correction: 7 of `OilMessage`'s 15 `case`s are reachable this way (`HEIGHT_OIL_ALARM`/`HHEIGHT_OIL_ALARM`/`LOW_OIL_ALARM`/`LLOW_OIL_ALARM`/`HEIGHT_WATER`/`HEIGHT_TEMPER` all flow into `saveAlarm`; `RELAY_DISCONNECT` reaches the DB through a separate direct call in `AsyManager2`'s error listener, gated by a runtime-toggleable preference, not a hardcoded-off branch) — see the corrected, per-`case` reasoning in `OilMessage.java` itself, not this file, before trusting any summary of which ones are live. Every unreachable one is still marked in place with a `[不可达-YYYY-MM-DD]` comment explaining the specific reason (`grep -rn "不可达-202"` to enumerate all of them regardless of date — a further round on 2026-09-23, prompted by the user naming a couple more suspects from the design draft directly, added `item_commit_work.xml`'s 5 keys, marked `[不可达-2026-09-23]` and attributed to the user's product-side confirmation rather than a code trace since the click path there is in fact wired, and confirmed via code that `MinOilCanView`'s `content[0]`/`oil_type_language` is computed but never drawn — the `i==0` loop iteration draws a tank-number badge instead and `continue`s past the generic label/value drawing); before spending translation (or any other) effort on a string, check whether its call site already carries one of these comments, and whether a later `[已更正-YYYY-MM-DD]` comment nearby supersedes an earlier one. If this file reappears in a landmine-hunting or i18n context: re-verifying "reachable" always means opening the class that owns the click/adapter and reading the method body, following the value all the way to wherever it's actually displayed or sent — and when a value has more than one call site, checking *all* of them before concluding "unreachable", not stopping once a couple come back dead. **2026-09-24 addendum, same root mistake in a new shape: a `<string>`'s Java-side `R.string.KEY` references being all-dead does not mean the key itself is dead — it can also be referenced declaratively via `android:text="@string/KEY"` in a layout XML, which is a completely separate consumer invisible to a Java-only grep.** `data_save_success` was deleted from all four `strings.xml` and its `custom_toast.xml` attribute stripped because both of its `R.string.data_save_success` Java call sites (`OilTankRepositoryImpl`'s and `DBDataManager`'s dead export handlers) were correctly dead — but nobody re-checked `custom_toast.xml`'s own inflation site before concluding the *layout* was dead too. It isn't: `BaseFragment.initWindowDialog()` inflates it unconditionally (called from `BaseFragment`'s own init path, so every real screen picks it up) and `showWindDialog()`/`showWindDialog(int)` display it from five live fragments (`BuLuFragment`, `OilCanSetFragment`, `OilTestFragment`, `SetBaseFragment`, `SetPawFragment`) as a generic "operation succeeded" popup — the user caught this by name. The general lesson: when a string is referenced from both Java and a layout's `android:text/hint/title`, its reachability is the *union* of both paths, not just whichever one you happened to grep for first — check `R.string.KEY` in `.java` **and** `@string/KEY` in `.xml` as two independent searches, then verify every layout that turns up by finding *that layout's own* inflate/`setContentView`/`<include>` site, not by assuming "the string's other references are dead so the layout must be too."

Each of these is pinned by an assertion in `CRCheckTest`/`DataUtilsTest`, so changing the behavior turns a test red rather than shipping silently.

## Signing

Release builds are signed via `app/build.gradle`'s `signingConfigs.release`, wired up 2026-08-16. The keystore file itself (`app/keystore/release.jks`) is untracked (`.gitignore`) and generated locally with `tools/generate-release-keystore.sh`; its store/key passwords and alias go through the same `local.properties`-injection channel as the other secrets (`sansen.releaseStorePassword`, `sansen.releaseKeyAlias`, `sansen.releaseKeyPassword` — see `local.properties.template`). If any of the three properties or the keystore file itself is missing, `assembleRelease` still succeeds (unsigned APK, same as before this existed) but logs a `[配置缺失]` warning — it does not hard-fail, matching the project's existing secret-handling convention.

Treat `release.jks` as the app's permanent production identity once generated: Android requires the *same* signing key for in-place upgrades of a given `applicationId`, so losing the file or its passwords means already-deployed devices can only be wiped and reinstalled, never upgraded. Back the keystore and passwords up somewhere outside this checkout (the generation script prints this reminder too).
